The chat endpoint returns a `StreamingResponse` immediately. As the engine runs, it yields SSE frames (text deltas, citation events, step or tool status) that the frontend consumes incrementally.

SSE works over plain HTTP with no upgrade handshake and passes through any proxy. For server→client-only streaming, WebSockets add complexity for no benefit.

---

## Event contract

Every frame is `event: <name>\ndata: <json>\n\n`.

Both engines emit the same contract. `tool` frames come only from the loop; `run`, `step` and `ticket_proposal` frames come only from the graph. Everything else is shared.

| Event | Payload | When | Engine |
|---|---|---|---|
| `run` | `{run_id, conversation_id}` | Once, before the first node | graph |
| `step` | `{seq, stage, status, level, reasoning, latency_ms, ts, …}` | As each node finishes | graph |
| `tool` | `{name, status: "start"\|"end"}` | Before and after each tool call | loop |
| `text` | `{delta: str}` | Each text chunk | both |
| `citation` | `{index, source, title, cited_text}` | Each inline citation | both |
| `ticket_proposal` | `{run_id, subject, category, product_area, priority, body}` | When a turn offers to file a ticket | graph |
| `done` | `{conversation_id, input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens, cost_usd, latency_ms}` | After DB commit | both |
| `error` | `{message: str}` | On any exception, instead of `done` | both |

A graph `done` frame carries four extra fields: `run_id`, `outcome`, `confidence` and `ticket_id`. `outcome` is `"answer"`, `"converse"` or `"ticket"`. It is three-way because a boolean cannot express *this was not a support question*.

`ticket_proposal` is an **offer**, not a record: the ticket has not been filed when it arrives. The client renders it as a card with a confirm button, which posts to `/api/c/{client_id}/runs/{run_id}/ticket`. Nothing about the ticket travels in that request. The draft stays in the graph's checkpoint, so a client can accept an offer but never author one.

### The `step` event

The payload is the same dict written to `Run.steps`, returned by the same call that persists it. [Runs & Durability](/configent/docs/runs-and-durability#a-step-entry) lists the node-specific fields.

```
event: step
data: {"seq": 2, "stage": "grade", "status": "ok", "level": 1, "reasoning": "The passages cover Cloud Run deployment…", "confidence": 0.05, "kind": "question", "latency_ms": 4110, "cost_usd": 0.0024}
```

**Unknown events are dropped silently** by the frontend's `handleEvent`, so backend work on a new event type stays invisible until the client learns to render it.

There is no `ticket` step in that stream. The graph is paused, and the step arrives on the run when the user confirms. `ticket_id` is `null` because nothing has been filed.

A turn that is not a support question leaves at Level 1:

```

event: done
data: {"conversation_id": "...", "run_id": "3f2b...", "outcome": "converse", "ticket_id": null, ...}
```

> **The escalation and converse replies are `text` events too.** A streaming client renders them exactly like an answer. Without them the UI shows a step trail above an empty bubble, which reads as a crash rather than a decision.

## FastAPI endpoint

```python
@router.post("/c/{client_id}/chat/stream")
async def chat_stream(client_id: str, req: ChatRequest):
    cfg = _client(client_id)
    engine = stream_graph if cfg.agent.mode == "graph" else stream_turn

    async def event_source():
        async with AsyncSessionLocal() as db:
            async for name, data in engine(
                req.message, cfg=cfg, client_id=client_id,
                conversation_id=req.conversation_id, db=db,
            ):
                yield f"event: {name}\ndata: {json.dumps(data)}\n\n"

    return StreamingResponse(
        event_source(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

One entry point, two engines, selected by `agent.mode`. The endpoint opens the DB session inside `event_source()`, not via `Depends(get_db)`, because a `Depends`-scoped session closes before `StreamingResponse` starts writing.

`X-Accel-Buffering: no` prevents nginx from holding the entire stream and releasing it as one chunk.

## How graph nodes stream

Graph nodes cannot `yield` to the endpoint: LangGraph runs them. They write to LangGraph's custom stream instead, and `stream_graph()` forwards what arrives.

```python
# inside a node
get_stream_writer()(("step", entry))
get_stream_writer()(("text", {"delta": event.delta.text}))

# stream_graph()
async for event, data in graph.astream(
    initial, thread, context=deps, stream_mode="custom", durability="sync"
):
    yield event, data
```

- **The custom mode, not `updates`.** An `updates` chunk arrives only when a node returns, after all its text deltas. The custom stream carries steps, deltas and proposals in the exact order the nodes wrote them, in one mode.
- **The tuples are the SSE events.** Nodes write the same `(event, data)` pairs the loop yields, so the endpoint and the frontend need no graph-specific code.
- **`done` and `error` come from `stream_graph()`, not a node.** They depend on persisting the turn after the graph stops, which happens outside it.

## The loop's `stream_turn`

`stream_turn` is an async generator that handles setup, error recovery and the `done` event:

```python
async def stream_turn(user_message, *, cfg, client_id, conversation_id, db):
    started = time.monotonic()
    conversation_id, history = await _prepare_conversation(db, client_id, conversation_id)
    result = LoopResult(messages=messages)
    try:
        async for event in _stream_loop(messages, ..., result=result):
            yield event
    except anthropic.APIError as exc:
        await db.rollback()
        yield ("error", {"message": f"Upstream API error: {exc.__class__.__name__}"})
        return
    except Exception as exc:
        await db.rollback()
        yield ("error", {"message": "An internal error occurred. Please try again."})
        return

    await _persist_turn(db, conversation_id, len(history), result)
    await db.commit()
    yield ("done", {"cost_usd": round(result.usage.cost_usd, 6), ...})
```

Errors call `db.rollback()` before yielding `error`. HTTP headers are already sent by that point, so there is no other way to signal failure. `stream_graph()` follows the same rule.

`_stream_loop` translates raw Anthropic SDK events into event tuples:

```python
async with aclient.messages.stream(**_request_kwargs(...)) as stream:
    async for event in stream:
        if event.type == "content_block_start":
            if event.content_block.type == "tool_use":
                yield ("tool", {"name": event.content_block.name, "status": "start"})
        elif event.type == "content_block_delta":
            if event.delta.type == "text_delta":
                yield ("text", {"delta": event.delta.text})
            elif event.delta.type == "citations_delta":
                yield ("citation", {"index": citation_index, ...})
    response = await stream.get_final_message()
```

`get_final_message()` returns the completed response after the stream closes, and its `usage` struct feeds cost accounting. `_stream_loop` emits `tool` `status: "end"` after `asyncio.gather` completes, so the frontend knows exactly when a tool call finishes.

## Frontend

`ChatPanel.tsx` uses `fetch` POST rather than `EventSource` (which is GET-only):

```typescript
const response = await fetch(`/api/c/${clientId}/chat/stream`, {
  method: "POST",
  body: JSON.stringify({ message, conversation_id: conversationId }),
  headers: { "Content-Type": "application/json" },
});

for await (const { event, data } of parseSse(response.body!.getReader())) {
  handleEvent(event, data);
}
```

`handleEvent` drives React state:

| Event | Effect |
|---|---|
| `tool start` / `tool end` | Shows and removes a "Searching…" indicator |
| `step` | Appends to the live step trail |
| `text` | Appends `delta` to the current message |
| `citation` | Attaches a numbered popover to the preceding text segment |
| `ticket_proposal` | Renders the confirm card |
| `done` | Stores `conversation_id`; renders cost and latency |
| `error` | Renders the error inside the assistant bubble |

Text and citations arrive interleaved, so the frontend builds `{ text, citations[] }` segments rather than a flat string.

## Next.js proxy route

Browser requests go to the Next.js API route at `apps/web/app/api/c/[client_id]/chat/stream/route.ts`, which proxies to FastAPI:

```typescript
export async function POST(req: Request, { params }) {
  const upstream = await fetch(
    `${process.env.API_URL}/api/c/${params.client_id}/chat/stream`,
    { method: "POST", body: req.body, duplex: "half" }
  );
  return new Response(upstream.body, {
    headers: { "Content-Type": "text/event-stream" },
  });
}
```

The proxy keeps the FastAPI origin off the browser and handles CORS in one place.

## Note: Streamable HTTP

Streamable HTTP is the MCP spec's replacement for HTTP+SSE as an MCP server transport. It lets a single endpoint respond with either plain JSON or an SSE stream, and adds session management.

That overhead suits MCP servers serving external clients like Claude Desktop, not a custom chat API with a fixed event contract that always streams. If Configent ever exposes its tools as an MCP server, Streamable HTTP would be the right transport for that surface.
