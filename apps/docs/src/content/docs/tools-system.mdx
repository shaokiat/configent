Tools are the extension points that let the agent do more than retrieve text. Each client YAML lists the tools available to its agent; the agent loop calls them as needed during a turn.

---

## Architecture

```
config/configent-support.yaml   tools/registry.py
  agent:                          _REGISTRY = {
    tools:                          "search_docs":           (DEFINITION, execute),
      - search_docs         →       "get_document":          (DEFINITION, execute),
      - get_document                "create_support_ticket": (DEFINITION, execute),
      - create_support_ticket       "pricing_lookup":        (DEFINITION, execute),
                                    "coverage_check":        (DEFINITION, execute),
                                  }
                                       │
                                  validated at startup
                                  (unknown names → ValueError, not 404)
```

A client's `agent.tools` lists a subset of the registry: the two shared tools plus any client-specific tools it needs. Configent Support uses the two shared tools plus its own
`create_support_ticket`.

The registry is a plain dict: no dynamic loading, no plugin system. Adding a tool means writing a module and adding one entry to `_REGISTRY`.

## Built-in tools

### `search_docs` (shared)

Semantic similarity search over the client's corpus. The primary retrieval tool. The system prompt instructs the agent to call it before answering any factual question.

```python
# Input
{"query": "PX900 chamber seal replacement interval", "k": 5}

# Output — Anthropic search_result blocks (enables inline citations)
[
  {
    "type": "search_result",
    "source": "corpus://acme-fab/spare-parts-catalog",
    "title": "Spare Parts Catalog",
    "content": [{"type": "text", "text": "...chunk text..."}],
    "citations": {"enabled": True}
  },
  ...
]
```

Empty retrieval returns a plain `text` block telling the model no documents matched. The system prompt instructs the model to say it doesn't know rather than hallucinate.

**`execute` doesn't retrieve. It delegates.** It calls `search()` and wraps the hits as `search_result` blocks. The retrieval itself lives one layer down.

```
search_docs.execute()
  │
  ├─ search()                 retrieval/search.py
  │    ├─ embed_query()       Voyage, query mode (not document)
  │    └─ pgvector cosine     scoped to client · drop below 0.3 floor
  │
  └─ wrap top-k hits as search_result blocks
```

> **Same embed/pgvector path as ingest.** See [Ingestion Pipeline → Search](/configent/docs/ingestion-pipeline#search) for the full details: embedding asymmetry, the k×2 over-fetch, and why the floor exists.

### `get_document` (shared)

Fetches the full text of a document by `document_id`. Used when a search chunk lacks enough context, for example when a procedure spans multiple sections.

```python
# Input
{"document_id": "a3f2b1c4"}

# Output
{"document_id": "a3f2b1c4", "title": "...", "source_uri": "...", "text": "..."}
```

Enforces `client_id` isolation: a document belonging to a different client returns a not-found error even if the ID is valid.

### `create_support_ticket` (configent-support)

The escalation tool for the Configent Support bot. When a question falls outside the docs, the agent files a ticket instead of guessing. It's a deterministic mock — the same `subject` + `category` always produce the same `ticket_id` (via `zlib.crc32`, not Python's `hash()`), so it's reproducible with no real backend.

```python
# Input
{"subject": "Ingestion fails when VOYAGE_API_KEY is unset", "category": "bug"}

# Output
{"ticket_id": "CONFIGENT-1042", "status": "open", "subject": "...", "category": "bug",
 "priority": "normal", "eta_hours": 8, "url": "https://support.configent.dev/tickets/CONFIGENT-1042"}
```

The system prompt instructs the model to file a ticket only when retrieval comes up empty — never as a substitute for searching. See [Adding a New Use Case](/configent/docs/adding-a-use-case) for the full build.

### `create_escalation_ticket` (gcp-platform-support)

The escalation tool for the support agent. Unlike the mock above, it makes a real HTTP
POST to a separate service — see [Mock Ticket Service](/configent/docs/mock-ticket-service)
for the service, its idempotency contract, and the chaos switches.

```python
# Input (drafted by the escalate stage, not by the answering model)
{"subject": "Cloud Run instance quota increase needed in europe-west1, blocking a deploy",
 "category": "quota_or_billing", "product_area": "cloud_run", "priority": "high"}

# Output (the service assigns the id)
{"ticket_id": "PLATFORM-1043", "status": "open", "queue": "platform-serverless",
 "eta_hours": 8, "url": "https://platform.internal.example/tickets/PLATFORM-1043", ...}
```

Two things make it unlike every other tool on this page:

**Its `DEFINITION` is never sent to a model.** This client runs
[Pipeline Mode](/configent/docs/pipeline-mode), where Python calls the executor directly at
one call site. The answering model's request has no `tools` key at all — asserted in a
test, not left to inspection. The definition stays in the file because the tool is
registered like any other and the schema documents the contract.

**It takes `run_id` and `stage_seq`.** They form the `Idempotency-Key`. Both are
keyword-only with defaults, so the free-form loop — which has no run — can still call the
tool; without a `run_id` no key is sent, which is correct, because without a run there is
nothing to deduplicate against.

### `pricing_lookup` (acme-fab)

Looks up unit price, volume discounts, and lead time for an Acme part number. Backed by a hardcoded catalog in the current implementation.

### `coverage_check` (meridian)

Checks whether a specific procedure or treatment is covered under a Meridian Insurance policy.

## Tool lifecycle in the agent loop

The [Agent Loop](/configent/docs/agent-loop#tool-execution) drives the full roundtrip; here is the tool's-eye view of it. When the model decides to call a tool, it returns a `tool_use` block in its response:

```json
{
  "type": "tool_use",
  "id": "toolu_01A2B3",
  "name": "search_docs",
  "input": {"query": "PX900 seal replacement interval", "k": 5}
}
```

The loop executes the tool and wraps the result in a `tool_result` block, which is appended as a `user` message for the next API call:

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A2B3",
  "content": [{"type": "search_result", ...}]
}
```

The `tool_use_id` must match the `id` from the model's block — the API validates this. Tools within a single iteration run concurrently via `asyncio.gather`. A tool that raises returns `{"error": "<message>"}` rather than crashing the turn.

## Adding a new tool

**1. Create the module** under `tools/<client_or_shared>/`:

```python
DEFINITION = {
    "name": "my_tool",
    "description": "...",
    "input_schema": {
        "type": "object",
        "properties": {
            "param": {"type": "string", "description": "..."},
        },
        "required": ["param"],
    },
}

async def execute(tool_input: dict, *, client_id: str, db) -> dict | list:
    return {"result": do_something(tool_input["param"])}
```

**2. Register it** in `tools/registry.py`:

```python
_REGISTRY = {
    ...
    "my_tool": (my_tool.DEFINITION, my_tool.execute),
}
```

**3. Add it to a client config:**

```yaml
agent:
  tools:
    - search_docs
    - my_tool
```

Unknown tool names in YAML fail at startup with a clear error — validation happens at config load time, not at request time.

## Return value conventions

| Return type | How it's sent to the model |
|-------------|---------------------------|
| `dict` or `list[non-block]` | `json.dumps(result)` as a text string in `tool_result.content` |
| `list[{"type": ..., ...}]` | Passed verbatim as `tool_result.content` blocks (enables `search_result` citation blocks) |

Use the content-block form when you need the model to emit citations. Use plain JSON for everything else.

## Tool definitions and caching

Tool definitions are sent with every API call, sorted alphabetically before inclusion. This ensures the tool list serializes identically regardless of YAML order — required for Anthropic's prefix-match prompt cache to hit. See [Prompt Caching](/configent/docs/prompt-caching) for details.
