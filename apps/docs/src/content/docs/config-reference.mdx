<div class="lead">
  Every Configent client is defined by a single YAML file in <code>config/</code> at the
  repo root. This page documents every key, its type, default, and valid values.
  All keys are validated against a Pydantic schema at startup — invalid configs fail fast
  rather than at request time.
</div>

## Top-level keys

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `client_id` | `string` | ✓ | Unique identifier. Used as the pgvector namespace, URL slug, and log prefix. Must match `^[a-z0-9][a-z0-9-]*[a-z0-9]$`. |
| `name` | `string` | ✓ | Human-readable client name. Used in logs and the UI header. |

Any other top-level key fails at load: a leftover `escalation:` beside `handoff:` would otherwise read like it does something.

```yaml
client_id: gcp-platform-support
name: "Cloud Platform Support"
```

> This page uses **Cloud Platform Support**, the client the repo ships, as its running example.
> Its file is `config/gcp-platform-support.yaml`.

## `branding`

Controls UI presentation for this client.

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `branding.logo` | `string` | ✓ | Path to the client logo, relative to the repo root. |
| `branding.primary_color` | `string` | ✓ | Hex colour used for the chat UI accent. |
| `branding.assistant_name` | `string` | ✓ | Name displayed in the chat header. |
| `branding.tagline` | `string` | | Empty-state copy. Unset, the UI falls back to a generic line. |
| `branding.suggested_questions` | `list[string]` | | Up to 5 starter questions shown on an empty chat. |

```yaml
branding:
  logo: assets/gcp-platform-support/logo.svg
  primary_color: "#1a73e8"
  assistant_name: "DeployBot"
  suggested_questions:
    - "My Cloud Run container fails to start — what does the PORT error mean?"
    - "Can you raise my Cloud Run instance quota for europe-west1?"
```

## `corpus`

Configures the document source and chunking settings.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `corpus.source` | `string` | — | Path to the document directory, relative to the repo root. `.md`, `.markdown`, `.txt`, `.docx`, `.pdf`, `.html` and `.htm` files are ingested recursively; other files are listed as unsupported in the ingest report. |
| `corpus.source_url_template` | `string` | `""` | Fallback citation link for a file with no `url:` front matter. `{stem}` and `{path}` (relative path, no extension) are filled in. Empty means plain-text citations. Joins the fingerprint when set. |
| `corpus.embedding.model` | `string` | `voyage-3` | Voyage AI model for chunks and questions alike. Must emit 1024 dimensions: `voyage-3`, `voyage-3-large` or `voyage-3.5`. Anything else fails at load. |
| `corpus.chunking.chunk_size` | `int` | `800` | Maximum tokens per chunk. Larger values preserve more context per retrieval hit. |
| `corpus.chunking.overlap` | `int` | `100` | Token overlap between adjacent chunks. Prevents mid-sentence splits from degrading retrieval quality. |
| `corpus.chunking.prefix_title` | `bool` | `false` | Start each chunk with `<title> — <heading path>`, before embedding and keyword indexing. Joins the fingerprint when on: turning it on rebuilds the index. |

```yaml
corpus:
  source: corpora/gcp-platform-support/
  embedding:
    model: voyage-3
  chunking:
    chunk_size: 512
    overlap: 64
```

**Supported file types:** `.pdf`, `.md` / `.markdown`, `.html` / `.htm`.

**Embedding:** requires a `VOYAGE_API_KEY` environment variable.

**Incremental ingestion:** ingest skips a file when its bytes and the `embedding`, `chunking` and `source_url_template` settings are unchanged. Edit a file and only that file is rebuilt. Change a setting and every file is rebuilt. Delete a file and its document is pruned. Until ingest runs after a settings change, chat answers `409 index_out_of_date`. See [Ingestion Pipeline](/configent/docs/ingestion-pipeline).

## `agent`

Selects the client's template with `agent.template` (required, no default) and tunes it. The keys below are the [support graph](/configent/docs/support-graph)'s (`template: documents`). Each template accepts only its own keys; the text-to-SQL keys are [in their own section](#agent-database) below.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `agent.template` | `string` | — | `documents` or `database`. A name with no registered template fails at load. |
| `agent.model` | `string` | — | OpenRouter model id, such as `anthropic/claude-haiku-4.5` or `deepseek/deepseek-v4.1-flash` (D14). It writes the cited answer, citing numbered passages as `[n]` (D15). Every model call in the graph uses it. It must have a row in [`config/pricing/claude.yaml`](#model-pricing), or startup fails. The shipped client runs `anthropic/claude-haiku-4.5`. |
| `agent.structured_model` | `string` | `agent.model` | Model for every structured-output call: grading, rewriting, SQL generation and repair, the ticket draft. Any model that follows a JSON schema, such as `deepseek/deepseek-v4.1-flash`; the cited answer runs on `agent.model`. Must have a price row (D14). |
| `agent.system_prompt_file` | `string` | — | Path to the answering prompt, relative to the repo root. `grade.md`, `rewrite.md` and `ticket_draft.md` must sit beside it. |
| `agent.max_tokens` | `int` | `4096` | Maximum output tokens for the answering call. The grade, rewrite and draft calls have fixed limits. |
| `agent.retrieval_drop_floor` | `float` | `0.3` | Similarity below which a retrieved chunk is **discarded** before the model sees it. Applied by `retrieve` and the dense half of Level 2. |
| `agent.escalate_below` | `float` | `0.45` | Similarity below which the best surviving chunk **fails Level 1**. Level 2 has no cosine floor. |
| `agent.confidence_threshold` | `float` | `0.6` | Groundedness score below which a level **falls short**. Applies at both levels. |
| `agent.corrective.enabled` | `bool` | `true` | Whether a turn that fails Level 1 gets [corrective retrieval](/configent/docs/corrective-retrieval) or goes straight to a ticket offer. |
| `agent.corrective.query_rewrites` | `int` | `3` | Query variants the Level 2 rewrite returns, each embedded and searched. Between 1 and 5. |

```yaml
agent:
  template: documents
  model: anthropic/claude-haiku-4.5
  system_prompt_file: prompts/gcp-platform-support/answer.md
  max_tokens: 2048
  retrieval_drop_floor: 0.3
  escalate_below: 0.45
  confidence_threshold: 0.6
  corrective:
    enabled: true
    query_rewrites: 3
```

> **Unknown keys fail at load.** `AgentConfig` forbids extra keys. `mode`, `tools` and `effort`
> belonged to the [retired loop engine](/configent/docs/retiring-the-loop), and a config that
> still sets one is rejected rather than silently ignored.

> **Falling short of a threshold does not file a ticket.** At Level 1 it sends the turn to
> Level 2, or to a conversational reply if the grader called it a greeting. At Level 2 it
> produces a drafted ticket the user is asked to confirm. See
> [The Guardrail](/configent/docs/escalation-guardrail).

> **`escalate_below` must exceed `retrieval_drop_floor`.** They act on the same number at
> different points: the drop floor discards, the escalate floor routes. If the escalate
> floor were the lower of the two, it could never fire, because every surviving hit is at or
> above the drop floor by construction. The config validator rejects that relationship at
> startup. See [The Guardrail](/configent/docs/escalation-guardrail).

> **One pass, no iteration cap.** A turn runs at most seven nodes: Level 1, Level 2, the
> ticket offer and the ticket itself.

## `agent` (database)

The [text-to-SQL template](/configent/docs/text-to-sql)'s keys (`template: database`). A `database` client takes no `corpus:` or `retrieval:` block; either one fails at load.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `agent.model` | `string` | — | OpenRouter id of a Claude model, priced in `config/pricing/claude.yaml` like any other. |
| `agent.structured_model` | `string` | `agent.model` | Model for every structured-output call: grading, rewriting, SQL generation and repair, the ticket draft. Any model that follows a JSON schema, such as `deepseek/deepseek-v4.1-flash`; the cited answer runs on `agent.model`. Must have a price row (D14). |
| `agent.system_prompt_file` | `string` | — | Path to `answer.md`; `generate.md` and `ticket_draft.md` must sit beside it. |
| `agent.max_tokens` | `int` | `4096` | Maximum output tokens for the answering call. |
| `agent.database.dialect` | `string` | — | `sqlite` only. A Postgres client would be a second dialect, not another template. |
| `agent.database.path` | `string` | — | SQLite file, relative to the repo root. A missing file is not a load error: chat answers 409 until it exists (`make data-bird` for the demo). |
| `agent.context.source` | `string` | — | The notes folder: `descriptions/<table>.csv`, `glossary.md`, `rules.md`. Merged with the introspected DDL into the schema context at ingest. |
| `agent.guard.row_limit` | `int` | `200` | Rows returned to the answering call; more are cut and the result says it was truncated. |
| `agent.guard.timeout_ms` | `int` | `5000` | A query still running after this is interrupted. SQLite has no statement timeout, so a progress handler enforces it. |
| `agent.repair_attempts` | `int` | `2` | Repairs allowed after a rejected or failed query before the turn escalates. Between 0 and 3. |

```yaml
agent:
  template: database
  model: anthropic/claude-haiku-4.5
  system_prompt_file: prompts/f1-analyst/answer.md
  database:
    dialect: sqlite
    path: data/bird/formula_1.sqlite
  context:
    source: corpora/f1-analyst/
  guard:
    row_limit: 200
    timeout_ms: 5000
  repair_attempts: 1
```

> **Changing the database or a notes file needs an ingest.** The schema context is
> fingerprinted from the DDL and the notes; until `make ingest` runs, chat answers 409.

## `handoff`

Required for every client. What happens when a turn can't be answered from the sources (D9, amended). The *decision* is the template's and is made in Python; this block picks only the action. The block is a union tagged by `mode`, so a ticket key under `mode: message` fails at load.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `handoff.mode` | `message` \| `ticket` | `message` | `message`: reply with fixed text, no ticket and no model call. `ticket`: draft a ticket, offer it, file it once on the user's confirmation. |
| `handoff.message` | `string` | — | `message` mode only, and required there. The whole reply; name a contact. |
| `handoff.categories` | `map` or `list` | — | `ticket` mode only, and required there. Ticket categories the draft may use. A map gives each id a label for the offer; a list uses the id with spaces. Must include `other`. |
| `handoff.product_areas` | `list[string]` | `[]` | `ticket` mode. Empty: the draft has no product-area field. |
| `handoff.queue` | `string` | — | `ticket` mode. Queue sent with the ticket. Unset, the ticket service routes by product area. |
| `handoff.team` | `string` | `platform team` | `ticket` mode. Who the offer and the failure message say will take the ticket. |
| `handoff.preamble` | `string` | `That one needs a human.` | `ticket` mode. First sentence of the ticket offer. |

```yaml
handoff:
  message: "I couldn't find that in the documentation. Email support@acme.com."
```

```yaml
handoff:
  mode: ticket
  queue: data-team
  team: data team
  categories: [missing_data, data_request, other]
```

A `message` turn's trail ends in a `decline` step and its outcome is `decline`; a `ticket` turn's ends in `escalate`, then `ticket` once confirmed.

## `retrieval` (optional)

How the index is queried (D12). Every key defaults to today's behaviour, and a file without the block loads and retrieves identically. All keys are query-side, so editing them needs no re-ingest. Unknown keys fail at load.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `retrieval.top_k` | `int` | `5` | Chunks kept per ranked list and after fusion. Must be above 0. |
| `retrieval.rrf_k` | `int` | `60` | Reciprocal rank fusion constant. Must be above 0. Only affects Level 2. |
| `retrieval.keyword.enabled` | `bool` | `true` | Whether Level 2 also runs full-text search on the rewrite's keywords. |

```yaml
retrieval:
  top_k: 5
  rrf_k: 60
  keyword:
    enabled: true
```

The drop floor and `escalate_below` stay under `agent:`: they are a validated pair of guardrail thresholds, not retriever parameters.

## Model pricing

```yaml
# config/pricing/claude.yaml — USD per million tokens
anthropic/claude-haiku-4.5:
  input: 1.00
  output: 5.00
  cache_write: 1.25   # the 5-minute TTL
  cache_read: 0.10
```

Every `cost_usd` in the system comes from this table: the step trail, the `done` event, the conversation total and the daily budget check. It is one file for the deployment, keyed by the exact model id a client config uses.

- **Checked in and dated.** Anthropic publishes prices on its [pricing page](https://platform.claude.com/docs/en/about-claude/pricing); no API returns them.
- **Copy every column.** Cache rates are listed per model; don't derive them from a multiplier.
- **An unpriced model fails startup.** The registry calls `price_for(agent.model)` for every client at load.
- **An estimate, not the bill.** Billed cost comes from the Admin API cost report. See [Decisions → Known gaps](https://github.com/shaokiat/configent/blob/main/docs/decisions.md#part-3--known-gaps).

## `limits`

Controls per-client rate limiting and cost guardrails.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `limits.rate_limit_per_minute` | `int` | `20` | Maximum requests per minute for this client. |
| `limits.daily_budget_usd` | `float` | `2.00` | Maximum spend in USD per day, at the rates in `config/pricing/claude.yaml`. Requests are rejected once the budget is exhausted. |

```yaml
limits:
  rate_limit_per_minute: 60
  daily_budget_usd: 2.00
```

## `evals` (optional)

Configures automated evaluation against a golden set. Omit if not using evals.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `evals.golden_set` | `string` | — | Path to a `.jsonl` golden set, relative to the repo root. |
| `evals.judge_model` | `string` | `anthropic/claude-sonnet-4.6` | Claude model used as the LLM judge for eval scoring. |

```yaml
evals:
  golden_set: evals/gcp-platform-support/golden.jsonl
  judge_model: anthropic/claude-sonnet-4.6
```

## Complete example

The shipped `config/gcp-platform-support.yaml`, with comments and the tagline trimmed:

```yaml
client_id: gcp-platform-support
name: "Cloud Platform Support"

branding:
  logo: assets/gcp-platform-support/logo.svg
  primary_color: "#1a73e8"
  assistant_name: "DeployBot"
  suggested_questions:
    - "My Cloud Run container fails to start — what does the PORT error mean?"
    - "Why won't my GKE node pool scale down after I deleted the workload?"
    - "Can you raise my Cloud Run instance quota for europe-west1?"

corpus:
  source: corpora/gcp-platform-support/
  embedding:
    model: voyage-3
  chunking:
    chunk_size: 512
    overlap: 64

agent:
  template: documents
  model: anthropic/claude-haiku-4.5
  system_prompt_file: prompts/gcp-platform-support/answer.md
  max_tokens: 2048
  retrieval_drop_floor: 0.3
  escalate_below: 0.45
  confidence_threshold: 0.6
  corrective:
    enabled: true
    query_rewrites: 3

handoff:
  mode: ticket
  categories:
    account_config: project configuration
    quota_or_billing: quota or billing
    incident: suspected incident
    access_request: access request
    docs_gap: documentation gap
    other: other
  product_areas: [cloud_run, gke, iam, other]
  preamble: >-
    That one needs a human: it depends on your own project configuration, and my
    knowledge base is public Google Cloud documentation only.

evals:
  golden_set: evals/gcp-platform-support/golden.jsonl
  judge_model: anthropic/claude-sonnet-4.6

limits:
  rate_limit_per_minute: 60
  daily_budget_usd: 2.00
```
