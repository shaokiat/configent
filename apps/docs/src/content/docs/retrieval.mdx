`retrieve` is Level 1's first node and makes no model call. It embeds the message, runs a cosine scan over the client's chunks, and discards anything below the drop floor. The node lives in `agent/graph.py`; the search is `search()` in `retrieval/search.py`.

The best surviving similarity is **signal 1** of the [guardrail](/configent/docs/escalation-guardrail).

---

## The flow

```
retrieve(state)
  │
  └─ search()                 retrieval/search.py
       ├─ embed_query()       Voyage, input_type="query"
       ├─ _dense()            pgvector cosine · WHERE client_id = ? · LIMIT k*2
       └─ floor filter        drop below retrieval_drop_floor, then [:k=5]
```

The node writes two things to state: the surviving hits, and `top_similarity`, which is `0.0` when nothing survived. Hits are stored as plain dicts (title, source URI, text, similarity) because the checkpointer saves state as JSON.

Level 2 reuses the `_dense()` half of `search()` inside `hybrid_search()`. See [Corrective Retrieval](/configent/docs/corrective-retrieval).

## A worked example

Two turns from one conversation, with drop floor `0.3` and escalate below `0.45`. A real run.

**Turn 1: "My Cloud Run container fails to start — what does the PORT error mean?"**

- Voyage embeds the message, and pgvector returns the 10 nearest chunks for this client.
- Five survive the floor. The best, from *Cloud Run: deployment and runtime errors*, sits at `0.62`.
- `0.62` clears `escalate_below`, so signal 1 passes and the turn goes to [grading](/configent/docs/grading). The node took 405 ms.

**Turn 2: "so is that the same as the health check timing out?"**

- The message is embedded as written. Nothing in it names Cloud Run or the PORT error.
- Two chunks survive the floor, the best at `0.36`, from the right document.
- `0.36` is under `escalate_below`. Level 1 falls short, and the turn goes to [Level 2](/configent/docs/corrective-retrieval), where a rewrite with the conversation in view finds the answer.

## Design decisions

### Retrieval is a node, not a tool

Agentic retrieval is for decisions with more than one right answer. This one has one: the model always needs context, so letting it choose adds failure modes without adding capability.

| | **Node (this graph)** | Tool call ([the retired loop](/configent/docs/retiring-the-loop)) |
|---|---|---|
| **Deciding to search** | Nothing to decide; it always happens | The model may skip it or mistime it |
| **Answering from memory** | Impossible, grounding precedes the model | Models sometimes reply from parameters |
| **Latency** | One embedding | Reason, emit, wait, resume, twice if it reformulates |
| **Replay** | Same message, same embedding, same top-k | A generated query differs per run |
| **Injection surface** | User text is embedded, never interpreted | An attacker influences what gets searched |
| **Multi-hop** | Not possible | The reason to choose it |
| **What the grader rates** | Exactly the passages the answerer will see | A moving target |

Switch to a tool when multi-hop pays off. Reformulating a bad query is not a reason to: Level 2 does that with a structured call, and keeps the search itself deterministic.

### Follow-ups are Level 2's job

Level 1 embeds the bare message. The retired pipeline prepended the previous user turn instead. The graph dropped that heuristic because Level 2 does the job properly.

| | Prepend the previous user turn (retired) | **Bare message, rewrite at Level 2 (built)** |
|---|---|---|
| **A follow-up at Level 1** | Often clears, for free | Usually falls short |
| **A three-turn reference chain** | Loses the subject | The rewrite sees the last six turns |
| **A change of subject** | The old subject pollutes the query | Nothing pollutes it |
| **Cost on a follow-up** | Nothing | A rewrite, a regrade, one embedding call: $0.039 against $0.026 in the live run |
| **Failure direction** | Escalates an answerable question | The same, one tier later |

### The search itself

- **Embedded as a question, not a document.** `input_type="query"` differs from the `"document"` type used at ingest, and Voyage exploits the asymmetry for recall. See [Ingestion Pipeline](/configent/docs/ingestion-pipeline#why-voyage-ai).
- **Over-fetch, then filter.** pgvector can't apply the floor inside the scan, so filtering in SQL would return fewer than `k` rows whenever the floor bites.
- **The floor makes "nothing matched" a case.** Zero survivors still go to the grader, which has to recognise a greeting. Python then overwrites its confidence with `0`.
- **`client_id` is in the `WHERE` clause.** Tenant isolation is a query predicate, not a convention. See [Multi-Tenancy](/configent/docs/multi-tenancy).

> **Reproducibility is scoped to one embedding model version.** "Same query, same top-k" holds while the model is fixed. `voyage-3` is hardcoded in `embed.py` and no version is recorded on the chunk or the step, so bumping it silently changes what old runs would retrieve today.

## Configuration

| Key | Default | What it does |
|---|---|---|
| `agent.retrieval_drop_floor` | `0.3` | Similarity below which a chunk is discarded. Also applied to the dense half of Level 2 |

`k` is fixed at 5. Full key list: [Config Reference](/configent/docs/config-reference#agent).

> **The floor and `escalate_below` are not the same knob.** The floor discards; `escalate_below` fails Level 1. They read the same number at different points, and their ordering is validated at startup. See [The Guardrail](/configent/docs/escalation-guardrail#three-thresholds).
