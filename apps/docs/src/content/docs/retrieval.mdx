`retrieve` is the first stage of the pipeline and the only one that makes no model call. It embeds the question, runs a cosine scan over the client's chunks, and discards anything below the drop floor. It lives in `agent/pipeline.py`; the search itself is `retrieval/search.py`, shared with the loop engine's `search_docs` tool.

Its second return value is **signal 1** of the [guardrail](/configent/docs/escalation-guardrail).

---

## The flow

```python
async def stage_retrieve(
    db: AsyncSession, *, cfg: ClientConfig, client_id: str, query: str
) -> tuple[list[Hit], float]
```

Returns the hits that survived the floor and `hits[0].similarity`, or `0.0` when nothing survived. Each `Hit` carries `document_title`, `source_uri`, `text`, `similarity`, and `chunk_index`, which is what the [answering stage](/configent/docs/answering) needs to build `search_result` blocks.

```
stage_retrieve()
  │
  ├─ _retrieval_query()       previous user turn + this one
  │
  └─ search()                 retrieval/search.py
       ├─ embed_query()       Voyage, input_type="query"
       ├─ pgvector cosine     WHERE client_id = ? · ORDER BY similarity · LIMIT k*2
       └─ floor filter        drop below retrieval_drop_floor, then [:k]
```

```python
similarity = (1 - Chunk.embedding.cosine_distance(query_vec)).label("similarity")
... .where(Chunk.client_id == client_id).order_by(similarity.desc()).limit(k * 2)
hits = [Hit(...) for row in rows if float(row.similarity) >= floor]
return hits[:k]
```

The loop engine reaches the same `search()` through `search_docs.execute()`, which wraps the hits as content blocks. One retrieval implementation, two callers, configured differently — the tool takes `search()`'s default floor, while this stage passes the client's. See [Tools System](/configent/docs/tools-system#search_docs-shared).

## Why not a retrieval agent tool?

Agentic retrieval is for decisions with more than one right answer. This one doesn't have that.

- **The need is unconditional, not discovered.** A tool call is worth it when the model *might* need context. Here it always does, so delegating only adds a failure mode: the agent skipping or mistiming the call.
- **It removes retrieval laziness.** Models sometimes decide they already know the answer and reply from parameters instead of searching. For an escalation flow that means a confident, invented resolution path. Grounding happens before the model gets a vote.
- **One embedding beats a round trip.** A tool call costs reason, emit, wait, resume, sometimes twice if the model reformulates. Escalation paths are usually SLA-bound.
- **The decision has to be defensible later.** Same question, same embedding, same top-k. A generative step produces different queries on different runs, leaving nothing fixed to replay when someone asks why a ticket was filed.
- **It shrinks the injection surface.** The question is user-written. Turning that text into a search query with a model hands an attacker influence over what gets retrieved.

### When it should be a tool call

- **Multi-hop pays off.** "Nothing above the threshold, try broader." A second search earns its keep here. That is the [loop engine](/configent/docs/agent-loop) and its `search_docs` tool, which Configent's three other clients run. This one uses neither.
- **The input is noisy.** Long logs, mixed languages, pasted boilerplate. The middle ground is one cheap call to extract a clean query, then a deterministic search. Still not agentic retrieval.
- **Ticket types need genuinely different corpora.** A stack trace wants code and logs, a billing dispute wants another index. That needs routing before retrieval, which neither engine has: a client points at one `corpus.source`, so a tool call alone would not fix it.

> **Why this client is the easy case.** It answers Cloud Run, GKE and IAM questions from one homogeneous set of public Google Cloud docs, and questions like "what does the Cloud Run PORT error mean?" embed well as written, so there is no index to choose and no query to rewrite. Its `category` and `product_area` enums do look like ticket types, but the escalate stage assigns them after retrieval to route the ticket to a queue, not to pick a corpus.

## Design

- **Deterministic, not a tool.** The model cannot skip retrieval or search for something else. That is what makes the groundedness score mean anything — the scorer always rates the same passages the answerer will see.
- **The query is embedded as a question, not a document.** `input_type="query"` differs from the `"document"` type used at ingest. Questions and answers have different linguistic patterns, and Voyage uses that asymmetry to improve recall. Free win, one argument. See [Ingestion Pipeline](/configent/docs/ingestion-pipeline#why-voyage-ai).
- **Over-fetch, then filter.** `limit(k * 2)`, drop below `retrieval_drop_floor` in Python, then truncate to `k`. pgvector cannot apply the floor inside the scan, so filtering in SQL would return fewer than `k` rows whenever the floor bites. With the default `k=5`, 10 rows come back and at most 5 go forward.
- **The floor exists so "nothing matched" is a case.** Without it the model always receives `k` chunks regardless of relevance. When the corpus does not contain the answer, those chunks are noise the model may hallucinate around.
- **`client_id` is in the `WHERE` clause.** Tenant isolation is a query predicate, not a convention. See [Multi-Tenancy](/configent/docs/multi-tenancy).

> **Follow-ups get the previous turn prepended.** "And what about GKE?" embeds to nothing useful when no model is rewriting the query. `_retrieval_query()` prepends the last user message: one line, no extra call. It is a heuristic, not query rewriting, and it fails on a three-turn reference chain. The alternative was a demo where the second question fails.

## Configuration

| Key | Default | What it does |
|---|---|---|
| `agent.retrieval_drop_floor` | `0.3` | Similarity below which a chunk is discarded before anyone sees it |

`k` is fixed at 5 in the pipeline. Full key list: [Config Reference](/configent/docs/config-reference#agent).

> **The floor and `escalate_below` are not the same knob.** The floor discards; `escalate_below` escalates. They read the same number at different points, and their ordering is validated at startup. See [The Guardrail](/configent/docs/escalation-guardrail#three-thresholds).

## Edge cases

- **Nothing survives the floor.** `stage_retrieve` returns `([], 0.0)`. The pipeline short-circuits past [scoring](/configent/docs/scoring) straight to the branch, which escalates with `"retrieval returned no passages above the drop floor"`. Asking a model to rate zero passages invents a number.
- **First turn of a conversation.** `_retrieval_query()` finds no previous user message and returns the question unchanged.
- **Non-string history content.** A prior turn stored as blocks rather than a string is skipped rather than coerced.

> **Reproducibility is scoped to one embedding model version.** "Same query → same top-k" holds while the embedding model is fixed. `voyage-3` is hardcoded in `embed.py` and no version is recorded on the chunk or the step, so bumping it silently changes what old runs would retrieve today. Replaying a historical decision would need the version pinned per record and a re-embed on change. Not built — the corpus has only ever seen one model.
