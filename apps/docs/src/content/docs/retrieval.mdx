`retrieve` is the first stage of the pipeline and the only one that makes no model call. It embeds the question, runs a cosine scan over the client's chunks, and discards anything below the drop floor. It lives in `agent/pipeline.py`; the search itself is `retrieval/search.py`, shared with the loop engine's `search_docs` tool.

Its second return value is **signal 1** of the [guardrail](/configent/docs/escalation-guardrail).

---

## The flow

```
stage_retrieve()
  │
  ├─ _retrieval_query()       previous user turn + this one
  │
  └─ search()                 retrieval/search.py
       ├─ embed_query()       Voyage, input_type="query"
       ├─ pgvector cosine     WHERE client_id = ? · ORDER BY similarity · LIMIT k*2
       └─ floor filter        drop below retrieval_drop_floor, then [:k]
```

Two things come back: the hits that survived the floor, and the similarity of the best one — `0.0` when nothing survived. Each hit carries its document title, source URI, text, similarity and chunk index, which is what the [answering stage](/configent/docs/answering) needs to build `search_result` blocks.

The loop engine reaches the same `search()` through `search_docs.execute()`, which wraps the hits as content blocks. One retrieval implementation, two callers, configured differently — the tool takes `search()`'s default floor, while this stage passes the client's. See [Tools System](/configent/docs/tools-system#search_docs-shared).

## A worked example

Two turns through the stage, with this client's thresholds: drop floor `0.3`, escalate below `0.45`. Similarity numbers are illustrative.

**Turn 1 — "What is the maximum request timeout on Cloud Run?"**

- `_retrieval_query()` finds no previous user turn and returns the question unchanged.
- Voyage embeds it; pgvector scans this client's chunks and returns the 10 nearest.
- Six sit below `0.3` and are dropped. Four go forward, the best at `0.61`.
- `0.61` clears `escalate_below`, so the turn continues to [scoring](/configent/docs/scoring).

**Turn 2 — "And what about GKE?"**

- On its own that embeds to almost nothing — no product, no subject, nothing matchable. Best hit `0.29`, below the floor, zero survivors, and the turn escalates on `"retrieval returned no passages above the drop floor"`. The corpus had the answer; the query never asked for it.
- `_retrieval_query()` prepends the previous user turn instead, so what gets embedded is:

  ```
  What is the maximum request timeout on Cloud Run?
  And what about GKE?
  ```

- That carries enough of the topic to reach the GKE timeout docs. Best hit `0.48`, above `escalate_below`, and the turn proceeds.

## Design decisions

### Retrieval is a function call, not a tool

Agentic retrieval is for decisions with more than one right answer. This one doesn't have that — the model always needs context, so letting it choose adds failure modes without adding capability.

| | Function call (this pipeline) | Tool call ([loop engine](/configent/docs/agent-loop)) |
|---|---|---|
| **Deciding to search** | Nothing to decide; it always happens | The model may skip it or mistime it |
| **Answering from memory** | Impossible — grounding precedes the model | Models sometimes reply from parameters |
| **Latency** | One embedding | Reason, emit, wait, resume — twice if it reformulates |
| **Replay** | Same question, same embedding, same top-k | A generated query differs per run |
| **Injection surface** | User text is embedded, never interpreted | An attacker influences what gets searched |
| **Multi-hop** | Not possible | The reason to choose it |
| **What the scorer rates** | Exactly the passages the answerer will see | A moving target |

Switch to a tool when multi-hop pays off, or when the input is noisy enough to need a cleaning pass first. Different question types needing different corpora is a third case, but a tool alone wouldn't fix it — that needs routing *before* retrieval, which neither engine has.

> **Why this client is the easy case.** One homogeneous set of public Google Cloud docs, and questions like "what does the Cloud Run PORT error mean?" embed well as written — no index to choose, no query to rewrite. Its `category` and `product_area` enums look like ticket types, but the escalate stage assigns them *after* retrieval, to route the ticket rather than to pick a corpus.

### The search itself

- **Embedded as a question, not a document.** `input_type="query"` differs from the `"document"` type used at ingest; Voyage exploits the asymmetry for recall. See [Ingestion Pipeline](/configent/docs/ingestion-pipeline#why-voyage-ai).
- **Over-fetch, then filter.** pgvector can't apply the floor inside the scan, so filtering in SQL would return fewer than `k` rows whenever the floor bites.
- **The floor makes "nothing matched" a case.** Without it the model always receives `k` chunks regardless of relevance — noise it may hallucinate around. With it, empty retrieval short-circuits past scoring to an escalation.
- **`client_id` is in the `WHERE` clause.** Tenant isolation is a query predicate, not a convention. See [Multi-Tenancy](/configent/docs/multi-tenancy).

### Follow-ups get the previous user turn prepended

Nothing rewrites the query, so a question that isn't self-contained retrieves nothing. `_retrieval_query()` prepends the last *user* message — a heuristic, not query rewriting. Every option below fails the same way, by escalating an answerable question; none can produce an ungrounded answer, since a thin query only lowers similarity. So the choice is purely about how often each one misfires.

| | Current turn only | **+ previous user turn** | + assistant reply |
|---|---|---|---|
| **Misfires when** | The question isn't self-contained | The subject changes *and* the new question is terse | The reply is long, or was wrong |
| **How often** | Every follow-up — most turns after the first | The rare intersection: terse questions are almost always follow-ups, not switches | Most turns — a 400-token reply swamps a 6-token question |
| **Extra cost** | — | — | Retrieval starts matching the model's own output |

- **Known limits.** Only the immediately preceding turn is used, so a three-turn reference chain still loses the subject, and its contribution scales with its length rather than its relevance.
- **The cheapest fix, unbuilt.** Embed both candidate queries and keep whichever scan scores higher: one batched call, no model, still replayable.

> **Reproducibility is scoped to one embedding model version.** "Same query → same top-k" holds while the model is fixed. `voyage-3` is hardcoded in `embed.py` and no version is recorded on the chunk or the step, so bumping it silently changes what old runs would retrieve today. Not built — the corpus has only ever seen one model.

## Configuration

| Key | Default | What it does |
|---|---|---|
| `agent.retrieval_drop_floor` | `0.3` | Similarity below which a chunk is discarded before anyone sees it |

`k` is fixed at 5 in the pipeline. Full key list: [Config Reference](/configent/docs/config-reference#agent).

> **The floor and `escalate_below` are not the same knob.** The floor discards; `escalate_below` escalates. They read the same number at different points, and their ordering is validated at startup. See [The Guardrail](/configent/docs/escalation-guardrail#three-thresholds).
