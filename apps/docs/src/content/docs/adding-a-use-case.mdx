  A new assistant is a new client: a config file, a sources folder, prompts and a logo. Each client
  runs one template, so the first choice is which. The real work is deciding what the sources can
  answer and writing prompts that hold that line. The two shipped clients are the worked examples:

## Step zero: choose the template

| If the evidence is | Template | Sources | Walkthrough |
|---|---|---|---|
| Documents | `documents` | `corpora/<id>/` | [DeployBot](/configent/docs/deploybot) |
| Rows in a SQL database | `database` | A SQLite file and a notes folder | [PitWall](/configent/docs/pitwall) |
| Something else | A new template | Whatever it needs | [Adding a Template](/configent/docs/adding-a-template) |

A new client of an existing template needs no Python. The anatomy below is the documents template's;
a database client swaps the corpus for `agent.database` and `agent.context`, and has three
prompts (`generate.md`, `answer.md`, `ticket_draft.md`).

---

## The anatomy of a client

| Artifact | Path | Controls |
|----------|------|----------|
| **Config** | `config/<id>.yaml` | Identity, branding, template, model, thresholds, handoff, limits |
| **Corpus** | `corpora/<id>/` | The documents the assistant answers from (`.md`, `.pdf`, `.html`) |
| **Prompts** | `prompts/<id>/` | `answer.md`, `grade.md`, `rewrite.md`, `ticket_draft.md` |
| **Branding asset** | `assets/<id>/logo.svg` | The logo shown in the chat UI |
| **Sentinels** *(recommended)* | `evals/sentinels.yaml` | Facts planted verbatim, so retrieval tests have ground truth |
| **Golden set** *(optional)* | `evals/<id>/golden.jsonl` | The expected outcome for each test question |

A model not yet in `config/pricing/claude.yaml` also needs a price row there.

## The one decision: what can the corpus never know?

The documents template answers what the corpus supports and hands off the rest. Write that
boundary down before writing a prompt.

| Answerable from documentation | Needs a human |
|---|---|
| What a default, limit or error message means | Anything about the user's own account or project |
| How a documented mechanism behaves | A change: quota, access, billing |
| Which documented cause fits a symptom | Whether an incident is happening right now |

Cloud Platform Support's corpus is public Google Cloud documentation. "What does the PORT error
mean?" is answerable. "Raise my quota" structurally is not, however relevant the retrieved
passages look. `grade.md` names that second column explicitly, which is what lets the grader
score it low.

## The recipe

1. **Plant the corpus** in `corpora/<id>/`. Strip markup so chunks hold prose. Keep each key fact on one line, so it survives chunking and can be cited word for word. Add `title:` and `url:` front matter if citations should link out.
2. **Plant sentinels.** Copy a few facts verbatim into `evals/sentinels.yaml`. `test_sentinels.py` checks each appears in its document and in no other client's corpus.
3. **Copy the prompts** from `prompts/gcp-platform-support/` and rewrite the domain parts. `grade.md` must name what the corpus can never know; that is what lets the grader score it low. The fields each prompt returns stay the same.
4. **Write the config.** Copy `config/gcp-platform-support.yaml`, then change `client_id`, `branding`, `corpus.source`, `handoff.categories` and `handoff.preamble`. Start with the default thresholds. Each line is explained on [DeployBot → The config](/configent/docs/deploybot#the-config-line-by-line).
5. **Add `assets/<id>/logo.svg`.** The UI reads `branding` from the API; there is no per-client build.
6. **Ingest and try one question per branch:** `make ingest CLIENT=<id>`, then open `/c/<id>`. Read the step trail, not only the answer.
7. **Write a golden set before tuning a threshold.** Tune against the set, not against one answer that looked wrong.

## What the platform validates for you

The registry checks every config when it first loads:

- **Config schema:** a malformed config fails with an error naming the field and the file.
- **Unknown keys fail.** A typo in an `agent` key, a key from the other template, or a leftover `tools` from the retired loop, is rejected rather than ignored.
- **An unpriced model fails.** `agent.model` must have a row in `config/pricing/claude.yaml`.
- **An unreachable guardrail fails.** An `escalate_below` at or under `retrieval_drop_floor` could never fire, so it is refused.
- **Tenant isolation** is enforced at the query level, filtering retrieval by `client_id`. See [Multi-Tenancy](/configent/docs/multi-tenancy).
