## The anatomy of a client

A new assistant is a new **client**: a tenant defined entirely by data, with no changes to the
engine for the common case. At most you create five things:

| Artifact | Path | Controls |
|----------|------|----------|
| **Config** | `config/<id>.yaml` | Identity, branding, model, corpus pointer, tool list, limits |
| **Corpus** | `corpora/<id>/` | The documents the assistant answers from (`.md`, `.pdf`, `.html`) |
| **System prompt** | `prompts/<id>.md` | Persona, grounding rules, when to use each tool |
| **Branding asset** | `assets/<id>/logo.svg` | The logo shown in the chat UI |
| **Golden set** *(optional)* | `evals/<id>/golden.jsonl` | Q&A pairs for offline quality checks |

If your assistant only needs to answer questions from documents, those files are everything — the
shared `search_docs` and `get_document` tools handle retrieval and citation, and you write **no
code**.

---

## The one decision: shared tools, or a client-specific tool?

Every client gets the shared tools for free. The only question is whether yours needs to *do*
something deterministic that retrieval can't:

- **Shared tools only** (`search_docs` + `get_document`) → a pure RAG assistant. Ask a question,
  get a cited answer from the corpus. No new code.
- **Add a client-specific tool** → when the assistant must return an auditable, structured result:
  look up a live price, return a deterministic verdict, file a ticket.

The shipped clients sit on that spectrum:

| Client | Client-specific tool | Why it needs one |
|--------|----------------------|------------------|
| **Acme Fab Equipment** | `pricing_lookup` | Return a real quote (price, discount, lead time) for a part |
| **Meridian Insurance** | `coverage_check` | Return an auditable covered / not-covered verdict for a claim scenario |
| **Cloud Platform Support** | `create_escalation_ticket` | File a ticket when a question depends on project state the docs can't know — invoked from the support graph, not chosen by the model |

**A quick checklist — you need a tool when the answer:**

1. Requires a calculation or lookup that isn't in the documents, **or**
2. Must be a structured, machine-checkable result (not prose), **or**
3. Triggers an action (file, send, create) rather than just informing.

If none of these are true, ship with the shared tools.

## Walkthrough: building the Acme Fab Equipment bot

Here's the exact sequence used to add the Acme Fab Equipment assistant.

> **A note on `config/disabled/`.** The demo deployment serves Cloud Platform Support alone, so
> Acme's config currently lives in `config/disabled/acme-fab.yaml` — a directory the registry does
> not read. Everything else about the client is unchanged, and moving the file up to `config/` and
> restarting the API brings it online. Write your own config straight to `config/`.

### 1. Plant the corpus

The corpus lives in `corpora/acme-fab/`: product overview, the PX-900 operations, maintenance and
troubleshooting manuals, the LT-200 operations manual, an installation guide, a process chemistry
guide, a spare parts catalog, and two FAQs.

> **Getting source documents into a corpus.** If your source is MDX/HTML, strip the frontmatter
> and any JSX/components so chunks contain prose, not markup. Keep each key fact on a single line
> so it survives chunking and can be cited verbatim. Remember the corpus is a *snapshot* — re-run
> ingestion to refresh it when the source changes.

Each client's corpus is isolated: a fact planted for one client is never retrieved for another.

### 2. Write the system prompt

`prompts/acme-fab.md` sets the persona (a senior field-service engineer for the PX-900 and LT-200
lines), the grounding rules (answer only from retrieved docs, cite the source, say "I don't know"
on empty retrieval), and — critically — *when to call the tool*: look a price up rather than
reading one out of a catalog chunk.

### 3. (If needed) add a client-specific tool

Acme needs live quotes, so it gets one tool. A tool is a small module that exposes a `DEFINITION`
(the Anthropic tool schema) and an async `execute` function:

```python
# apps/api/app/tools/acme_fab/pricing_lookup.py
from typing import Any

DEFINITION = {
    "name": "pricing_lookup",
    "description": "Look up the unit price, volume discount, and lead time for an Acme part ...",
    "input_schema": {
        "type": "object",
        "properties": {
            "part_number": {"type": "string"},
            "quantity":    {"type": "integer", "default": 1},
        },
        "required": ["part_number"],
    },
}

async def execute(tool_input: dict[str, Any], **_) -> dict:
    # Canned catalog data — deterministic, and agrees with the spare-parts sentinel facts.
    part = _CATALOG[tool_input["part_number"]]
    return {"unit_price_usd": part["unit_price_usd"], "lead_time_days": ..., ...}
```

Then register it **once** in the tool registry:

```python
# apps/api/app/tools/registry.py
from app.tools.acme_fab import pricing_lookup

_REGISTRY = {
    # ...shared + other client tools...
    "pricing_lookup": (pricing_lookup.DEFINITION, pricing_lookup.execute),
}
```

That one line makes the name available to configs. Use the shipped `pricing_lookup` as a
copy-paste template for your own tool. Keep tools **deterministic** — they should return
structured data the agent can cite, not invent business facts.

### 4. Write the config

`config/acme-fab.yaml` ties it together and lists exactly the tools the assistant should have:

```yaml
client_id: acme-fab
name: "Acme Fab Equipment"

branding:
  logo: assets/acme-fab/logo.svg
  primary_color: "#1B4F8A"
  assistant_name: AcmeAssist

corpus:
  source: corpora/acme-fab/
  chunking:
    chunk_size: 800   # larger chunks → whole procedure steps survive intact
    overlap: 100

agent:
  model: claude-haiku-4-5-20251001   # fast + cheap is right for factual lookup
  system_prompt_file: prompts/acme-fab.md
  max_tokens: 4096
  effort: medium
  tools:
    - search_docs
    - get_document
    - pricing_lookup

limits:
  rate_limit_per_minute: 20
  daily_budget_usd: 2.00
```

### 5. Add a branding asset

Drop a `logo.svg` into `assets/acme-fab/`. The UI reads `branding` to render a chat that
looks like the client's own product.

### 6. (Optional) add a golden eval set

`evals/acme-fab/golden.jsonl` holds Q&A pairs — including a refusal case the corpus can't answer —
so you can measure grounding before shipping a change. See
[Citations](/configent/docs/citations) for how grounding is evaluated.

### 7. Ingest and try it

```bash
make ingest CLIENT=acme-fab   # or just restart the API — it ingests on startup
```

Open `/c/acme-fab` and ask away. Re-running ingest is safe: unchanged documents are
skipped, changed ones are re-embedded.

## What the engine validates for you

You don't wire any of this manually — the platform checks it at startup:

- **Config schema:** the platform validates it; a malformed config fails boot with an error naming the field and
  the file.
- **Tool names fail fast.** Every name in `agent.tools` is checked against the registry. An unknown
  tool name stops startup — it can never reach a live user. (See [Tools](/configent/docs/tools-system).)
- **Tenant isolation:** the platform enforces it at the query level, filtering retrieval by `client_id`, so a
  client can only ever see its own corpus. (See [Multi-Tenancy](/configent/docs/multi-tenancy).)

## New use case in five steps

```text
corpora/<id>/            1. Drop in documents
prompts/<id>.md          2. Write the system prompt
apps/api/app/tools/<id>/ 3. (only if needed) add + register a client-specific tool
config/<id>.yaml         4. Write the config, listing the tools to enable
assets/<id>/logo.svg     5. Add branding → make ingest CLIENT=<id>
```

No code change for a documents-only assistant. No deployment pipeline. If something doesn't
validate, the startup error names the field and the file.
