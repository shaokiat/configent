The agent loop lives entirely in `apps/api/app/agent/loop.py`. No LangChain, LangGraph, or SDK tool runner. One file covers tool execution, cost tracking, prompt caching, and SSE streaming.

This is a standard **tool-use loop**, like ReAct without the explicit reasoning traces. The model signals intent through the API's `stop_reason` field instead.

## Entry points

```python
stream_turn(user_message, *, cfg, client_id, conversation_id, db)
    → AsyncIterator[tuple[str, dict]]   # (event_name, data)

run(user_message, *, cfg, client_id, conversation_id, db)
    → (conversation_id, LoopResult)
```

`stream_turn` is the frontend path. `run` is for tests and internal tooling. Both share the same logic.

## How the loop works

<Mermaid diagram={`
flowchart TD
    A[Call Anthropic API] --> B{stop_reason?}

    B -->|end_turn| C[Collect text + citations]
    C --> D([Return to caller])

    B -->|tool_use| E[Execute tools concurrently]
    E --> F[Append tool_results to messages]
    F --> A
`} />

Before the loop starts, it loads conversation history from Postgres (or creates a new `Conversation` row) and persists the user message.

Each iteration calls the Anthropic API and branches on `stop_reason`. The model sets that field; the loop has no say in it.

```python
if response.stop_reason == "end_turn":
    return collect_text_and_citations(response)

if response.stop_reason == "tool_use":
    tool_results = await asyncio.gather(*[execute(b) for b in tool_blocks])
    messages.append({"role": "user", "content": tool_results})
    continue  # loop again

raise RuntimeError("exceeded max iterations")
```

- **`end_turn`:** collect text and citations, return.
- **`tool_use`:** run the requested tools concurrently, append results, loop again.
- **8 iterations without finishing:** raise `RuntimeError`. A safety cap; normal queries resolve in 2–3 iterations.

After the loop, it writes the turn's new messages back to Postgres. The final assistant message stores its citation segments in a `citations` JSON column.

## Request assembly

Each API call includes the system prompt with `cache_control: ephemeral` and a `_with_turn_breakpoint` marker on the message history.

**Effort and thinking are model-dependent.** Extended thinking works only on Sonnet 4+ and Opus 4+. The loop sets `thinking: disabled` and the configured `effort` only when the model is *not* Haiku:

```python
# loop.py — effort/thinking are only supported on Sonnet 4+ and Opus 4+
if "haiku" not in cfg.agent.model:
    kwargs["thinking"] = {"type": "disabled"}
    kwargs["output_config"] = {"effort": cfg.agent.effort}
```

For non-Haiku models, the loop sets `effort` explicitly. Left to default, the API uses `high` effort with thinking enabled. That adds latency without quality gain for a chat assistant. Every shipped client runs Haiku, so this branch never executes and the `effort` key in their configs is inert. See [Config Reference](/configent/docs/config-reference#agent) for the caveat.

Caching details: [Prompt Caching](/configent/docs/prompt-caching).

## Tool execution

When the model stops with `tool_use`, the loop resolves each requested tool, runs it, and appends the output as a `tool_result` for the next call. The loop is only the orchestrator. It never knows what a tool *does*. Each tool is a registered executor with its own definition and logic.

**[Tools System](/configent/docs/tools-system)** covers how tools are defined, registered, and added. This section covers only how the loop *runs* them.

**Tools run concurrently.** One coroutine per tool block, all awaited at once; results come back in input order and append as a single `user` message.

```python
tool_results = await asyncio.gather(
    *[_execute_tool(b, client_id=client_id, db=db)
      for b in _tool_use_blocks(response.content)]
)
messages.append({"role": "user", "content": list(tool_results)})
```

The concurrency is real because every executor bottoms out in a database query (`await search(db, ...)`, `await db.execute(...)`). The event loop suspends each coroutine at its `await` and resumes it when Postgres responds, so multiple tools are in-flight at once without threads.

In practice the model usually calls one tool per iteration, so the gather is over a list of one. **Errors are contained:** an executor that raises returns `{"error": "..."}` to the model rather than crashing the loop, so the turn continues.

## Cost tracking

```python
@dataclass
class UsageTotals:
    input_tokens: int = 0
    output_tokens: int = 0
    cache_creation_input_tokens: int = 0
    cache_read_input_tokens: int = 0

    @property
    def cost_usd(self) -> float:
        return (
            self.input_tokens * 3.00
            + self.output_tokens * 15.00
            + self.cache_creation_input_tokens * 3.75
            + self.cache_read_input_tokens * 0.30
        ) / 1_000_000
```

The loop calls `UsageTotals.add()` after every API call. By the time it exits, `cost_usd` covers all iterations, including intermediate tool-call roundtrips.

> The per-token rates are hardcoded Sonnet list prices. Shipped clients run Haiku (cheaper), so the
> reported `cost_usd` is a deliberate **upper bound**: accurate enough for a cost badge, not billing.

## Example: one `search_docs` call

```
# iteration 1 — model calls search_docs
anthropic call client=acme-fab input=312 output=87 cache_creation=2048 cache_read=0

# iteration 2 — final answer
anthropic call client=acme-fab input=89 output=651 cache_creation=0 cache_read=2048
```

Two API calls, one `LoopResult`. The `done` SSE event reports the aggregated totals.
