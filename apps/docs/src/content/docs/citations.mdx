When the agent answers, every claim carries a citation to the passage it came from. The model writes the citation as a number; Python turns the number into the chip (D15).

---

## How it works

```
retrieved chunks / query rows
  └─ numbered passages: "[1] title (source)\n text"   → any model, via OpenRouter
        └─ the answer, citing with [n]                  → streamed back
              └─ Markers: [n] → citation event          → the UI, live
                    └─ segments                         → stored in the DB
```

### 1. Numbered passages

`answer_request_kwargs()` in each template returns the request and its passages. The user message is the passages, numbered in order, then the question:

```
[1] Cloud Run: deployment and runtime errors (https://cloud.google.com/run/docs/troubleshooting)
Container failed to start. Failed to start and then listen on the port defined by the PORT environment variable.

[2] …

Question: what does the PORT error mean?
```

The database template sends one passage, `[1]`: the query's rows as a table, titled with the query's reasoning and sourced as `sql://<client_id>`.

### 2. The model cites with `[n]`

The answer prompt asks for a marker after each sentence that uses a passage, `[1][2]` for several, numbers from the list only, and no sources list at the end. Any model OpenRouter lists can do this; Haiku 4.5 and DeepSeek V4.1 Flash both answered the demo questions with valid markers.

### 3. `Markers` parses the stream

`Markers` in `agent/common.py` reads the streamed text:

- **A valid `[n]` becomes a `citation` event,** and the marker leaves the text, with the space before it. "1 vCPU [1]." reads "1 vCPU." with a chip.
- **A marker split across chunks still parses.** A trailing `[`, `[1` or space is held back until the next chunk settles it.
- **A number with no passage stays in the text,** as written, and is counted in the answer step's `bad_citations`. So `arr[0]` in an answer about code survives, and a model inventing `[9]` shows in the step trail.

**What this does not check:** that passage `[n]` says what the sentence does. The marker is the model's claim. D15 records the trade, and the decision log's Known gaps names the check that would close it.

### 4. Segments

`segments_from()` turns the parsed pieces into a `segments` list: each run of text, then the citations that follow it. The shape is the one the UI and stored messages have always used:

```json
[
  {
    "text": "That error means the container never listened on the port Cloud Run expects",
    "citations": [
      {
        "source": "https://cloud.google.com/run/docs/troubleshooting",
        "title": "Cloud Run: deployment and runtime errors",
        "cited_text": "Container failed to start. Failed to start and then listen on the port defined by the PORT environment variable."
      }
    ]
  },
  {"text": ". Read the port from `PORT` rather than hardcoding it.", "citations": []}
]
```

`cited_text` is the cited passage, trimmed by `excerpt()` to a ~400-character, sentence-boundary preview.

### Linkable sources

A citation's `source` is the document's URL when it has one, else the `corpus://` identity. The URL is the passage's `source`, shown in its numbered header and carried onto the citation, so there is no extra SSE field.

- **Where the URL comes from:** `url:` in the file's YAML front matter, else `corpus.source_url_template` (`{stem}` and `{path}`, the relative path without extension), else none.
- **Stored on the document** (`documents.url`), carried on `Hit`, sent by `_hit_dict` and `answer_request_kwargs`. `source_uri` stays the stable identity that prune and the fingerprint key on.
- **The UI** renders a `source` starting with `http://` or `https://` as a link (new tab, `rel="noopener"`), anything else as plain text.
- **The GCP corpus** carries `title:` and `url:` in front matter, so DeployBot's citations open the upstream Google Cloud page. The CC BY 4.0 attribution stays in the body.

Segments with empty `citations` are plain text. Segments with citations render with inline source links in the frontend.

## Storage

The assistant message stores the reply in two columns of the `messages` table:

| Column | Contents |
|--------|----------|
| `content` | The reply text |
| `citations` | `{"segments": [...]}`, the frontend-friendly segments list |

Reloading a conversation renders straight from `segments`, with no post-processing.

---

## Empty retrieval

The answering call never runs with zero passages. Both route functions require at least one before they choose `answer`, so an empty retrieval goes to Level 2, a conversational reply, or a ticket offer. There is no uncited answer to guard against.

---

## Frontend rendering

Citations stream. As `Markers` completes each valid marker, the `answer` node writes a `citation` SSE event between the `text` deltas:

```json
// citation event payload
{"index": 1, "source": "https://cloud.google.com/run/docs/troubleshooting",
 "title": "Cloud Run: deployment and runtime errors", "cited_text": "Container failed to start. Failed to start and then listen on the port..."}
```

```
SSE events:  text · text · citation#1 · text · citation#2 · text · done
                    └──────────── frontend folds ───────────┘     (usage only)
segments:    [ {text, citations:[#1]}, {text, citations:[#2]}, … ]
```

The frontend rebuilds `{text, citations[]}` segments from the interleaved stream and renders each inline, with a badge that expands to the source title and the passage. The same pieces build the stored `segments` on the server, so a reloaded conversation renders what the live one did. The `done` event carries no `reply` or `segments`.

See [SSE Streaming](/configent/docs/sse-streaming) for the full event contract.
