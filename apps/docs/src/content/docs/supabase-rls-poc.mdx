## What this brings to the project

Configent isolates Clients by convention today: every table has a `client_id` column, and
every query is trusted to filter on it. That filter has never been wrong, but it's never been
*checked* either: a missed `WHERE` clause in a new query would ship silently. **Row-Level
Security (RLS)** turns that convention into a database-enforced guarantee, backed by
**Supabase Auth**, which issues the JWT a policy needs something to check against. That's a
stronger claim than "we always remember to filter."

---

## How RLS changes the isolation model

Supabase runs on plain Postgres, so it hosts the same schema unmodified. What moves is where
the `client_id` filter is enforced: from a line of application code to a policy the database
itself checks on every row.

| Layer | Today | Target |
|-------|-------|-----|
| Database | Self-hosted Postgres + pgvector | Supabase Postgres + pgvector (same extension) |
| Client isolation | `client_id` column, filtered by app code | Same column, enforced by RLS policy |
| DB role FastAPI connects as | Superuser (`postgres`) | Non-privileged `authenticated` role — superuser bypasses RLS entirely |
| Request → Client binding | `client_id` path param, trusted | JWT claim, verified per request |
| Agent loop, tools, SQLAlchemy models | Unchanged | Unchanged |

The important row is the third one. RLS is a no-op if the connection holds a role that
bypasses it, which is exactly what a superuser or Supabase's `service_role` does. With that
role swapped, a query that forgets the `WHERE client_id = ...` clause returns zero rows
instead of another Client's data.

Concretely, this is the exact query `search_docs` runs today, in `retrieval/search.py`: cosine
similarity over `chunks`, scoped to one Client.

### Current implementation

<Mermaid diagram={`
flowchart LR
    C["Client: acme-fab\\n(client_id from a trusted path param)"] --> Q["search_docs()"]
    Q --> S["WHERE chunks.client_id = 'acme-fab'"]
    S --> R["Returned: only acme-fab's chunks —\\nbecause the app remembered the WHERE"]
`} />

That `WHERE chunks.client_id = 'acme-fab'` is the only thing standing between this query and
another Client's rows. Drop it during a bad refactor, forget it in a new endpoint, or
copy-paste it into a new query without noticing, and nothing else catches the mistake.

<Callout tone="warning" title="Risk: every future query has to remember this too">
Nothing in the schema or the connection requires the `WHERE client_id` clause. Every query
path has to keep including it correctly, forever: `ingest.py`, `search.py`, every router, and
everything written after them. One miss is a data leak, not a bug ticket.
</Callout>

### Target: RLS-enforced

Same query, same missing-clause scenario, but with RLS turned on for the `chunks` table:

<Mermaid diagram={`
flowchart LR
    C2["Client: acme-fab"] --> Q2["search_docs()\\nno WHERE client_id clause"]
    Q2 --> P2{"RLS policy checks\\nevery row's client_id"}
    P2 -->|"client_id = acme-fab"| R1["✅ Returned"]
    P2 -->|"client_id = other clients"| R2["❌ Filtered out"]
`} />

Same result as before, but now it doesn't depend on the app code getting the `WHERE` clause
right. The database enforces the boundary whether the query asks for it or not, which is the
guarantee this evaluation is testing.

## Policies

### Auth model for this evaluation

Configent has no end-user auth today: chat is anonymous, scoped only by the `client_id` path
param. Full end-user accounts are out of scope for testing RLS. This evaluation uses the smallest
thing that gives a policy something to check: one JWT per Client, carrying a `client_id` claim,
attached to the connection FastAPI already holds open.

Supabase Auth issues tokens to a logged-in *user*, not a Client, so getting `client_id` into
one needs the smallest possible login: one Supabase Auth account per Client, not per human,
created with `client_id` set in that account's `user_metadata`. A **Custom Access Token
Hook** — a Postgres function Supabase calls every time it mints a token — copies
`user_metadata.client_id` into the JWT's claims:

<Mermaid diagram={`
flowchart LR
    A["Client account: acme-fab\\n(one login per Client)"] --> B["Supabase Auth\\nsign-in"]
    B --> C["Access Token Hook reads\\nuser_metadata.client_id"]
    C --> D["JWT issued with\\nclient_id claim"]
`} />

This is real auth, not a hand-signed stand-in, but it's still the smallest version: one
shared account per Client, no individual end users yet. Extending it to real end-user
accounts later is the same hook, keyed off a real human's login instead of a shared one; see
[What this unlocks later](#what-this-unlocks-later).

#### Current implementation

<Mermaid diagram={`
flowchart LR
    A["Request: /c/acme-fab/chat"] --> B["client_id = 'acme-fab'\\n(path param, unverified)"]
    B --> C["App trusts it,\\nfilters every query manually"]
`} />

The path param is never checked against anything: it's just a string the app trusts came
from the right place. There's no session, no signature, nothing a policy could key off.

#### Target: JWT-verified

<Mermaid diagram={`
flowchart LR
    A["JWT claim: { client_id: acme-fab }"] --> B["SET LOCAL request.jwt.claims = '...'"]
    B --> C["RLS policy reads current_setting('request.jwt.claims')\\nand compares it to the row's client_id column"]
`} />

This is not the admin/operator auth model discussed for the later UI work; that's a separate
role layered on top of this. But the claim itself is real, verified per request, not a
trusted string the app just believes.

#### What this unlocks later

The path param can't grow into more than a trusted string. A verified claim can, without
another rewrite of the isolation layer:

- **Admin/operator accounts:** add a `role` claim alongside `client_id` and write policies
  that check it, reusing the same Access Token Hook instead of building a second auth system
  for the admin UI.
- **Individual end-user accounts:** swap the one-login-per-Client account for real per-human
  logins, add a `user_id` claim, and scope `conversations` to the user who started them, not
  just the Client, using the same `EXISTS`-join policy shape already used for `messages` and
  `traces`.
- **Passwordless login for Client accounts:** magic links or OAuth swap in under the same
  hook without changing how any policy reads `client_id`.
- **An audit trail with a real identity attached:** today a `traces` row only proves which
  Client asked; a verified claim means it can also prove which authenticated session did.

### Tables in scope

Every table that already carries `client_id`, plus two that inherit scope through a join:

<Mermaid diagram={`
flowchart TD
    subgraph Direct["Direct client_id column — column compare"]
        T1[clients]
        T2[documents]
        T3[chunks]
        T4[conversations]
        T5[eval_runs]
    end
    subgraph Joined["Scoped via conversation_id — EXISTS join"]
        T6[messages] -.-> T4
        T7[traces] -.-> T4
    end
`} />

| Table | Policy |
|-------|--------|
| `clients` | Row visible only if `id` matches the JWT claim |
| `documents` | Row visible only if `client_id` matches |
| `chunks` | Row visible only if `client_id` matches (hot path for `search_docs`) |
| `conversations` | Row visible only if `client_id` matches |
| `messages` | Via `conversation_id` join to a client-scoped `conversations` row |
| `traces` | Via `conversation_id` join, same as `messages` |
| `eval_runs` | Row visible only if `client_id` matches |

Policy shape is the same for every direct-`client_id` table:

```sql
create policy client_isolation on chunks
  using (client_id = current_setting('request.jwt.claims', true)::json->>'client_id');
```

`messages` and `traces` have no `client_id` column of their own: they're scoped through
`conversation_id`, which is a second policy shape (an `EXISTS` join, not a column compare):

```sql
create policy client_isolation on messages
  using (exists (
    select 1 from conversations c
    where c.id = messages.conversation_id
      and c.client_id = current_setting('request.jwt.claims', true)::json->>'client_id'
  ));
```

This is a performance question, not just a correctness one: every `messages`/`traces` read
pays a per-row subquery unless the planner pushes the join predicate down.

### Application-layer changes

- `database.py` connects as a non-superuser Postgres role instead of `postgres`, so RLS
  actually applies.
- Each request issues `SET LOCAL request.jwt.claims` inside the same transaction as the
  query, after verifying the JWT.
- SQLAlchemy queries in `ingest.py`, `search.py`, and the routers are otherwise untouched:
  they already filter by `client_id`, so RLS makes that filter mandatory rather than trusted.
- The CLI ingestion path (`app.cli ingest --client`) runs outside a request context, so it has
  no JWT to attach. It gets its own credential on `service_role` (RLS bypass) instead of an
  authenticated, Client-scoped role, mirroring how it already takes `--client` as a trusted
  argument today.

<Callout tone="warning" title="Boundary: the CLI still bypasses RLS">
That's deliberate, not an oversight, but it means the CLI stays a second, unguarded write
path into the same tables the rest of this evaluation proves are isolated for request traffic.
</Callout>

## Out of scope

- **Admin UI for config and document upload:** separate proposal, deferred until this
  evaluation is validated.
- **Supabase Storage for corpus files:** ingestion keeps reading from `corpora/<client_id>/`
  on disk.
- **End-user accounts:** the chat widget stays anonymous.
- **Migrating off self-hosted Postgres in production:** this is an evaluation, not a
  commitment to switch.

## Open questions

- Does the Access Token Hook re-run on token refresh, or only at initial sign-in? If
  `user_metadata.client_id` changes, does an already-issued session pick it up, or does it
  need a forced re-login?
- Who provisions the one Supabase Auth account per Client, and where does its password or
  invite link live? Out of scope for the demo, but a real workflow question the moment this
  moves past one hard-coded test account.
- Does Supabase's connection pooler (pgbouncer, transaction mode) preserve `SET LOCAL`
  correctly, or does it require session mode for RLS claims to stick?
- Does RLS force `search_docs` off its HNSW index? (see below)
- Does `DEV_CONFIG_RELOAD`-style local iteration still work against a hosted Supabase
  instance, or does this evaluation need a local Supabase CLI stack?

### Performance risk: RLS vs. the HNSW index

<Mermaid diagram={`
flowchart TD
    Q["search_docs query\\n+ RLS predicate"] --> D{Planner chooses}
    D -->|"client_id first"| S["Sequential scan\\nHNSW index lost"]
    D -->|"HNSW first"| H["Walk HNSW graph,\\nfilter after"]
    H --> R{"Enough of this\\nClient's rows in top-k?"}
    R -->|"no"| Risk["❌ Recall risk:\\nfewer than k results"]
    R -->|"yes"| OK["✅ Correct results"]
`} />

`chunks` has an HNSW index (`ix_chunks_embedding_hnsw`, `vector_cosine_ops`) for ANN cosine
search, separate from the btree on `client_id`. An RLS predicate forces the planner to pick
one: filter by `client_id` first and lose the ANN index, or walk the HNSW graph first and
filter after.

<Callout tone="warning" title="Risk: fewer than k results, not just slower ones">
If the planner walks HNSW first, too many of the top candidates can belong to other Clients,
returning fewer than `k` real matches. Run `EXPLAIN ANALYZE` on a representative query to
confirm which plan Postgres picks before calling this safe to demo. If it drops the HNSW
index, try `SET LOCAL hnsw.iterative_scan` (pgvector ≥0.7): it keeps walking the graph past
RLS-filtered candidates until `k` real matches are found instead of giving up early.
</Callout>
