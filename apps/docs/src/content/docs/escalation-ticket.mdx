When the [guardrail](/configent/docs/escalation-guardrail) escalates, two stages run. `escalate` drafts the ticket fields with a structured-output call. `ticket` POSTs them to the ticket service. The model drafts; Python files.

The decision was already made before either stage started. Neither of them can revisit it.

---

## The flow

```
guardrail → escalate + why
  │
  ├─ stage_escalate()       structured output, shared _structured_call()
  │    └─ ticket_draft.md   → subject, category, product_area, priority, body
  │
  └─ stage_ticket()         get_tool_executor("create_escalation_ticket")
       └─ POST /tickets     Idempotency-Key: {run_id}:{stage_seq}
            └─ the service assigns the ticket id
```

The draft call is given the question and the guardrail's reason string — never a choice about whether to escalate. The tool is registered like any other, but its `DEFINITION` is never sent to a model: Python invokes the executor directly.

---

## A worked example

**"Can you raise my Cloud Run instance quota for europe-west1?"** — continuing from the [guardrail](/configent/docs/escalation-guardrail#a-worked-example), which escalated on groundedness `0.05`.

- `escalate` drafts the fields: `category: quota_or_billing`, `product_area: cloud_run`, `priority: high`, plus a subject and body. The step records the guardrail's reason alongside them.
- `ticket` POSTs the draft with `Idempotency-Key: {run_id}:4`. The service returns `PLATFORM-1043`, queue `platform-serverless`, ETA 8 hours.
- The reply is emitted as a `text` event, so a streaming client renders it the same way it renders an answer.

What the user ends up seeing:

```
Searched the documentation    best match 0.50 — above the escalate floor
Scored the evidence           groundedness 0.05 — below the 0.60 threshold
Escalated to a human          quota_or_billing · priority high
Filed a ticket                PLATFORM-1043
```

## Design decisions

### Python files the ticket, the model does not

The ticket tool exists in the registry, and the answering model never sees it.

| | **Direct executor call (built)** | Tool-use round trip |
|---|---|---|
| **Call sites to make idempotent** | Exactly one | As many as the model has turns |
| **Can the model decline to file?** | No — it is not asked | Yes |
| **Extra round trips** | None | One at minimum, more if it retries |
| **What the trail records** | One `ticket` step, always | Whatever the model happened to do |

### Idempotency comes from the run, not the content

- **The key is `{run_id}:{stage_seq}`.** Stable across a crash and retry of the *same* run, distinct across every other one.
- **Never derived from content.** Two people phrasing a request identically must not collide into one ticket.
- **A duplicate POST after a crash returns the original.** Same run, same stage, same key — the service hands back the ticket it already made. That path is the reason the key is not content-derived. See [Runs & Durability](/configent/docs/runs-and-durability).
- **The server assigns the ticket id.** The schema is owned on the other side of a network hop that can fail. The service is a mock we wrote ([Mock Ticket Service](/configent/docs/mock-ticket-service)); the *integration shape* is not mocked.
- **`run_id` and `stage_seq` are keyword-only with defaults.** The loop engine has no run, so it can still call the tool. Without a `run_id` no key is sent, which is correct — with no run there is nothing to deduplicate against.

### Failing the ticket does not fail the turn

- **HTTP failures are returned, not raised.** A 5xx comes back `{"error": ..., "retryable": True}`; a 4xx is our bug and is marked non-retryable. The run finishes with a `ticket` step marked `failed` rather than dying.
- **Retry is deliberately absent.** The executor makes one attempt and reports retryability. Retry with backoff belongs next to the dead-letter decision, not buried inside a tool.
- **The user is told the truth.** When filing fails, the reply says the question needs a human *and* that the ticket system could not be reached — not a fabricated ticket id.
- **An escalation is not a refusal.** The reply explains that the question depends on the user's own project, which a public-documentation corpus cannot cover, and points at the ticket.
