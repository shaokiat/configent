`answer` runs when the [guardrail](/configent/docs/escalation-guardrail) says the evidence holds. It sends the retrieved passages and the question to the model with citations enabled, and streams the reply. `answer_request_kwargs()` in `agent/pipeline.py` assembles the request.

The interesting part of that request is what is missing from it.

---

## Contract

```python
def answer_request_kwargs(
    cfg: ClientConfig, *, hits: list, question: str, history: list[dict]
) -> dict
```

```python
{
    "model": cfg.agent.model,
    "max_tokens": cfg.agent.max_tokens,
    "system": [{"type": "text", "text": ..., "cache_control": {"type": "ephemeral"}}],
    "messages": history + [{"role": "user", "content": content}],
}
```

There is no `tools` key. Not an empty list — the key never appears, and the string `"escalat"` appears nowhere in the request. A test asserts both, rather than leaving it to inspection.

---

## The flow

```
answer_request_kwargs()
  │  _search_result_blocks(hits) + [{"type": "text", "text": question}]
  ▼
Messages API (streaming, citations enabled)
  │  citations_delta ──▶ SSE `citation` event, as it arrives
  ▼
_collect_segments(response) ──▶ (text, citations, segments)
```

```python
content = _search_result_blocks(hits) + [{"type": "text", "text": question}]
```

Passages first, question last. `_collect_segments()` produces the same shape the loop engine produces, so the renderer and the stored format are unchanged by which engine ran.

---

## Design

- **Tool starvation is the mechanism, not the prompt.** The model is given no tool definitions, so it cannot file a ticket and cannot decline to answer by escalating instead. Prompting a model not to do something it is capable of doing is a request; removing the capability is a guarantee.
- **`search_result` blocks go in as top-level user content.** They do not have to arrive inside a `tool_result`. That API fact is what lets retrieval be an ordinary function call while citations keep working exactly as they do in the loop. Without it the pipeline would need a fake tool round trip to get citations.
- **Citations are enabled unconditionally.** The API requires citations on all search results in a request or none, and an uncited answer is not what this assistant is for.
- **The system prompt is cached.** One `cache_control` breakpoint on a block that does not change between turns. See [Prompt Caching](/configent/docs/prompt-caching).
- **The response object is assembled, not generated.** Citations and `output_config.format` cannot be combined, so this stage cannot return structured output. Python builds and validates the final response from the stage results — the stronger claim anyway, since the contract is constructed rather than hoped for.

---

## Edge cases

- **This stage never sees empty retrieval.** The guardrail escalates first. The loop engine handles the empty case differently, because there the model is still holding tools — see [Citations → Empty retrieval](/configent/docs/citations#empty-retrieval).
- **A model that answers without citing.** The passages are present and citations are on, so this reads as a corpus problem rather than a wiring one. The `n_citations` field on the step is what makes it visible.

## On the record

```json
{ "stage": "answer", "n_citations": 3,
  "reasoning": "similarity 0.71 and groundedness 0.88 both above threshold",
  "usage": { "input_tokens": 4210, "output_tokens": 260, "cost_usd": 0.00142 } }
```

`reasoning` is the guardrail's own sentence for the *not*-escalating case, so a successful answer is as justified in the trail as a refusal.
