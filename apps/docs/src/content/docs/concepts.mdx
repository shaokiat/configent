## The one-sentence version

Configent is a **RAG assistant** you configure with a **YAML file** instead of code. Drop in some
documents, write a short prompt, and you get a chat assistant that answers questions **grounded in
those documents** and **cites its sources** — with one deployment serving many isolated clients.

Everything below unpacks the bolded terms.

---

## RAG — Retrieval-Augmented Generation

An LLM only knows what it was trained on. **RAG** fixes that by *retrieving* relevant text from
*your* documents and handing it to the model alongside the question, so the answer is grounded in
your content rather than the model's memory.

```
question  ─►  find the most relevant document passages  ─►  give them to Claude  ─►  grounded answer
              (retrieval)                                    (augmented generation)
```

Why it matters: the assistant can answer questions about documents Claude has never seen — a
product manual, a policy wording, Configent's own docs — and it can refuse ("I don't know") when the
documents don't contain the answer, instead of guessing.

---

## Embeddings — turning text into numbers

To find "the most relevant passages," the system needs to compare meaning, not keywords. An
**embedding** is a list of numbers (a *vector*) that captures the meaning of a piece of text. Texts
with similar meaning get similar vectors — even if they share no words.

Configent uses **Voyage AI** (`voyage-3`, 1024 numbers per vector) to embed text. The same model
embeds documents at ingest time and questions at query time, so the two are directly comparable.

> Why a separate provider? Anthropic has no embeddings API; any RAG stack needs a separate embedder. → [Ingestion Pipeline](/configent/docs/ingestion-pipeline#stage-3--embed)

---

## Chunking — splitting documents into searchable pieces

You can't embed a whole 40-page PDF as one vector. The meaning blurs and citations become useless. **Chunking** splits a document into smaller passages (a few hundred tokens each) before
embedding, so retrieval can return *the exact paragraph* that answers a question.

- **`chunk_size`** — how big each piece is, in tokens. Smaller = more precise lookups; larger =
  more context per hit.
- **`overlap`** — how much text is repeated between neighbouring chunks, so a sentence split across a
  boundary still appears whole in at least one chunk.

Configent Support uses small chunks (`512` / `64`) because its docs are short, factual Q&A.
→ [Ingestion Pipeline](/configent/docs/ingestion-pipeline#stage-2--chunk)

---

## Vector search & pgvector — finding the nearest passages

Once every chunk is a vector, finding relevant text is a math problem: which stored vectors are
*closest* to the question's vector? "Closeness" is measured by **cosine similarity** (how aligned two
vectors point). The closest chunks are the most relevant passages.

**pgvector** is the Postgres extension that stores those vectors and runs the nearest-neighbour
search — so the whole stack stays on one database, no separate vector service.

```
[question] ─► Voyage ─► [vector] ─► pgvector finds nearest chunk vectors ─► top 5 passages
```

A **similarity floor** (0.3) drops weak matches, so "no good results" is an explicit, handled case
rather than noise the model might hallucinate over.
→ [Ingestion Pipeline](/configent/docs/ingestion-pipeline#search)

## Tools — letting the agent act, not just retrieve

A **tool** is a function the model can choose to call. Claude doesn't run code itself. It asks for a tool by name with arguments, the backend runs it, and the result returns to the conversation.

Configent has two kinds:

- **Shared tools** — every client gets these: `search_docs` (the retrieval step above) and
  `get_document` (fetch a full document when a chunk isn't enough).
- **Client-specific tools** — bespoke actions for one client. Configent Support's
  `create_support_ticket` files a ticket when the docs can't answer. Acme Fab's `pricing_lookup`
  quotes a part.

The rule of thumb: add a tool when the answer needs a **calculation, lookup, or action** that isn't
in the documents. Otherwise the two shared tools are enough.
→ [Tools System](/configent/docs/tools-system) · [Adding a New Use Case](/configent/docs/adding-a-use-case)

## The agent loop — how a turn actually runs

The **agent loop** is the back-and-forth between the backend and Claude for a single user message:

```
1. Send the question (+ system prompt + tool list) to Claude
2. Claude either answers  ──► done
   or asks to call a tool ──► run it, send the result back ──► go to step 1
```

This repeats until Claude produces a final answer (usually after one `search_docs` call), capped at
8 iterations for safety. There's no framework — it's a plain loop, so cost, streaming, and tool
execution are all visible in one file.
→ [Agent Loop](/configent/docs/agent-loop)

---

## System prompt — the assistant's standing instructions

The **system prompt** is a text file (`prompts/<client>.md`) that sets the assistant's persona and
rules: who it is, that it must answer *only* from retrieved documents, that it must cite sources, and
*when* to use each tool (e.g. "file a ticket only when the docs can't answer"). It's the same on
every turn, which is why it caches well (below).

---

## Citations — showing the receipts

A grounded answer is only trustworthy if you can see *where* it came from. Configent uses Anthropic's
native **citations**: when the loop passes retrieved passages as `search_result` blocks, Claude annotates
its answer with markers pointing at the exact sentences it used. The UI renders these as inline,
hoverable source links — not a footnote dump.
→ [Citations](/configent/docs/citations)

---

## Multi-tenancy — one deployment, many isolated clients

A **client** (or **tenant**) is a single assistant — its documents, branding, prompt, tools, and
limits — defined by one YAML file. **Multi-tenancy** means one running deployment serves many of them
side by side, fully isolated: `client_id` scopes every database query, so one client's documents can never appear in another's retrieval.

Adding a client is a no-code operation: a config file, a folder of documents, a prompt.
→ [Multi-Tenancy](/configent/docs/multi-tenancy) · [Config Reference](/configent/docs/config-reference)

---

## SSE streaming — words appearing as they're generated

Rather than waiting for the whole answer, the assistant **streams** it — text appears token by token,
and a "Searching…" indicator shows while a tool runs. This uses **Server-Sent Events (SSE)**, a
simple one-way "server keeps sending" channel over plain HTTP. The frontend reads the stream and
updates the chat live.
→ [SSE Streaming](/configent/docs/sse-streaming)

---

## Prompt caching — not paying twice for the same prefix

Every turn re-sends the system prompt and the full conversation history. **Prompt caching** tells
Anthropic to remember the unchanged *prefix* of the prompt for a few minutes, so Anthropic bills those tokens ~10× cheaper on the next turn instead of reprocessing them from scratch. It's why a long
conversation doesn't get linearly more expensive.
→ [Prompt Caching](/configent/docs/prompt-caching)

---

## Effort — how hard the model "thinks"

**Effort** controls Claude's extended-thinking budget (`low` → `max`). Higher effort spends more
tokens reasoning before answering. One caveat: extended thinking is only
available on Sonnet 4+ and Opus 4+, so the `effort` key has **no effect on Haiku** — which every
shipped client uses today.
→ [Config Reference](/configent/docs/config-reference#agent)

## Putting it together

Here's a single Configent Support turn, using every concept above:

```
You ask: "How do I add a new client?"
   │
   ├─ system prompt + tool list sent to Claude        (cached prefix → cheap)
   ├─ Claude calls search_docs("add a new client")    (agent loop, iteration 1)
   │     └─ question embedded (Voyage) → pgvector finds nearest chunks (RAG retrieval)
   │           scoped to configent-support only        (multi-tenancy)
   ├─ passages returned as search_result blocks
   ├─ Claude writes the answer, citing the chunks      (citations)
   └─ answer streams back token by token               (SSE)
```
