The guardrail is a function. No model is consulted, and none can override it:

```python
def should_escalate(*, retrieval_confidence, score, cfg) -> tuple[bool, str]:
    if score is None:
        return True, "retrieval returned no passages above the drop floor"
    if retrieval_confidence < cfg.agent.escalate_below:
        return True, f"top similarity {retrieval_confidence:.2f} < escalate_below ..."
    if float(score["confidence"]) < cfg.agent.confidence_threshold:
        return True, f"groundedness {...:.2f} < confidence_threshold ..."
    return False, "... both above threshold"
```

It returns the decision and the reason. The reason is recorded on the step, so every escalation carries its own justification.

## Two signals, not one

| Signal | Source | Catches |
|---|---|---|
| **Retrieval similarity** | `hits[0].similarity` from pgvector | Nothing in the corpus is close to the question |
| **Groundedness** | A cheap model scoring the retrieved passages | The right document came back, and it doesn't contain the answer |

Either one failing forces escalation. The second signal is the one that earns its keep, and the week 1 exit gate is the clearest illustration:

> **The observed case.** For "can you raise my Cloud Run instance quota for europe-west1?", retrieval scored **0.50** — above the 0.45 escalate floor, so the first signal passed. Groundedness came back **0.05**, and that forced the branch. The corpus has plenty of documentation *about* Cloud Run quota; it has nothing about *this user's* quota. Similarity alone cannot tell those apart.

## Three thresholds, two jobs

`retrieval_drop_floor` and `escalate_below` are easy to confuse, and confusing them silently disables the guardrail.

| Key | Default | Job |
|---|---|---|
| `retrieval_drop_floor` | `0.3` | **Discards** weak chunks before the model sees them |
| `escalate_below` | `0.45` | **Escalates** when the best surviving chunk is still weak |
| `confidence_threshold` | `0.6` | **Escalates** when the scorer says the passages don't support an answer |

The first two operate on the same number at different points in the flow, so their relationship matters:

```python
if self.mode == "pipeline" and self.escalate_below <= self.retrieval_drop_floor:
    raise ValueError(...)
```

If `escalate_below` were less than or equal to `retrieval_drop_floor`, the similarity signal could never fire. Every surviving hit is at or above the drop floor by construction, so `hits[0].similarity` would always clear the escalate threshold — and the only remaining path to escalation would be an empty result set. The config validator rejects that relationship at startup rather than letting a demo quietly lose half its guardrail.

## The scoring stage

`score` is a single structured-output call against a schema:

```python
{
    "supported":    {"type": "boolean"},
    "confidence":   {"type": "number"},
    "missing_info": {"type": "string"},
    "reasoning":    {"type": "string"},
}
```

It runs on the client's configured model — Haiku, which supports structured outputs and costs a fraction of a Sonnet call. The prompt lives in its own file, `prompts/<client_id>/score.md`, separate from the answer prompt.

That separation is the point. A single mega-prompt covering retrieval, scoring, and answering makes the scoring step unauditable, and scoring *is* the guardrail.

> **`supported` is not the signal.** The branch reads `confidence`, a number, and compares it to a configured threshold. A boolean from the model would move the threshold decision back inside the model, which is the thing this design is avoiding.

## What the user sees

An escalation is not an error, and it doesn't render as one. The reason string reaches the UI on the `score` and `escalate` steps, so the trail reads as a decision with a justification:

```
Searched the documentation    best match 0.50 — above the escalate floor
Scored the evidence           groundedness 0.05 — below the 0.60 threshold
Escalated to a human          quota_or_billing · priority high
Filed a ticket                PLATFORM-1043
```

The escalation reply is also emitted as a `text` event, so a streaming client renders it the same way it renders an answer. Without that, the UI would show a step trail above an empty message bubble — which reads as a crash rather than a decision.
