The guardrail is the only branch in the pipeline, and it is plain Python. `should_escalate()` reads the two signals produced by [retrieval](/configent/docs/retrieval) and [scoring](/configent/docs/scoring), compares them to configured thresholds, and returns the decision **and the reason for it**.

No model is consulted, and none can override it. This is the component the whole engine exists to make possible.

---

## The flow

<Mermaid diagram={`
flowchart TD
    A[should_escalate] --> B{score is None?}
    B -->|yes — retrieval was empty| E[Escalate]
    B -->|no| C{top similarity &lt; escalate_below?}
    C -->|yes — signal 1| E
    C -->|no| D{groundedness &lt; confidence_threshold?}
    D -->|yes — signal 2| E
    D -->|no| F[Answer]
`} />

Three checks, evaluated in order. Two things come back: the decision, and a human-readable sentence saying which check produced it — recorded on the step and rendered in the UI, so every escalation carries its own justification.

---

## A worked example

Three questions from the same client, one down each path.

**"My Cloud Run container fails to start — what does the PORT error mean?"**

- Similarity `0.71`, above `escalate_below: 0.45`. Groundedness `0.88`, above `confidence_threshold: 0.6`.
- Both checks pass, so the turn [answers](/configent/docs/answering). The reason recorded is *"similarity 0.71 and groundedness 0.88 both above threshold"* — a successful answer is as justified in the trail as a refusal.

**"Can you raise my Cloud Run instance quota for europe-west1?"** — a real trace:

- Similarity `0.50`. Above the floor, so signal 1 **passes**: the corpus does have a quotas-and-limits page, and it matched.
- Groundedness `0.05`. Signal 2 fails, and that forces the branch — the corpus documents Cloud Run quota in general, and says nothing about *this user's* quota.
- Recorded reason: *"groundedness 0.05 < confidence_threshold 0.6"*.

**A question about something the corpus has never covered**

- Nothing survives the drop floor, so scoring was skipped and `score is None`.
- The first check fires: *"retrieval returned no passages above the drop floor"*. No model was called at all on this path.

The middle case is the one that justifies the whole design. Similarity alone would have answered it.

## Design decisions

### Why two signals, not one

Each signal alone fails in a way the other one covers.

| | Similarity only | Groundedness only | **Both (built)** |
|---|---|---|---|
| **Nothing in the corpus is close** | Caught | Caught | Caught |
| **Right document, wrong content** | Missed — answers from a near-miss | Caught | Caught |
| **Deterministic?** | Yes | No — a model call | Half, and the half that can't fail open |
| **Cost** | Free | One cheap call | One cheap call |
| **Failure mode** | Confident answers to unanswerable questions | The guardrail rests entirely on a model judging a model | — |

Groundedness is the signal that earns its keep, but putting the *entire* guardrail behind a model call is what the deterministic signal exists to prevent.

### The decision, and the record of it

- **The reason string is a product feature, not a log line.** It is the answer to "why did it escalate?", generated by the comparison that made the decision, and it renders in the step trail the user sees.
- **The escalate path never asks a model whether to escalate.** The `escalate` stage drafts ticket fields *after* this function has decided. See [Escalation & Ticket](/configent/docs/escalation-ticket).
- **Empty retrieval is checked first.** The scoring call was skipped, so there is no number to compare.
- **A malformed score escalates.** `score.get("confidence", 0.0)` — a judgement missing its number fails toward the human, which is the correct default for a support agent.
- **There is no `branch` step in the trail.** The decision is recorded as the reason on the stage it produced, keeping the trail one entry per unit of work.

## Configuration

<a id="three-thresholds"></a>

| Key | Default | Job |
|---|---|---|
| `retrieval_drop_floor` | `0.3` | **Discards** weak chunks before the model sees them |
| `escalate_below` | `0.45` | **Escalates** when the best surviving chunk is still weak |
| `confidence_threshold` | `0.6` | **Escalates** when the scorer says the passages do not support an answer |

The first two operate on the same number at different points, so their ordering matters. Every surviving hit is at or above the drop floor by construction, so if `escalate_below <= retrieval_drop_floor`, signal 1 can never fire — the guardrail would look configured and be half dead. The config validator rejects that relationship at startup.

Setting both escalation thresholds to `0` is legal, and disables escalation for everything except empty retrieval. That is a deliberate config choice, so the validator allows it. Keys in full: [Config Reference](/configent/docs/config-reference#agent).
