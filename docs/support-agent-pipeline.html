DeployBot escalation pipeline

The support agent answers Cloud Run, GKE and IAM questions from public documentation — and when it can’t answer confidently, the code decides to escalate. Not the model.

client: gcp-platform-support 2 model calls / run 0 model-driven tool calls

The stage machine

Four stages, executed in order, with exactly one branch. The branch is an if statement — the answering model is never shown the ticket tool, so it can neither escalate nor decline to.

Why retrieval left the tool loop

Today the model decides to call search_docs, and citations ride back inside a tool_result. That makes retrieval a model decision — which is fine for exploratory work and fatal for a guardrail, because a run that never retrieves has nothing to score.

The Messages API accepts search_result blocks as top-level user content, not only inside a tool result. So retrieval becomes a plain function call and the blocks go straight into the answer request. Citations behave identically.

Citations and structured outputs are mutually exclusive

Setting output_config.format alongside citations returns a 400. That splits cleanly along stage lines — score and ticket-draft take structured output, answer takes citations — but it means SupportAnswer, the final contract with answer, citations[], confidence, escalated and ticket_id, cannot be a model output. Python assembles it from the stage results and validates it there. That’s the stronger version of the claim anyway: the response contract is constructed, not generated and hoped for.

The trap worth avoiding on day one

Run state commits on its own session so a crash can’t erase it. But the conversation row it points at is still sitting uncommitted in the request session — so the foreign key has no parent yet.

Three things to settle before writing pipeline.py

  • Two floors, not one. search() already drops hits below 0.3. The new escalation floor is a different question asked of the surviving hits. If the escalation floor sits below the drop floor it can never fire — hits[0] is ≥ 0.3 by construction, or hits is empty. Name them retrieval_drop_floor and escalate_below so nobody reasons this out twice.
  • Empty retrieval is its own branch. Zero hits means there is nothing to score. Escalate straight away and skip the model call entirely — cheaper, and honest about what happened.
  • Multi-turn breaks deterministic retrieval. “And what about GKE?” embeds to nothing useful. Query rewriting is on the cut list, so the cheap fix is to embed the previous user message alongside the current one when history exists. One line, no extra call.
